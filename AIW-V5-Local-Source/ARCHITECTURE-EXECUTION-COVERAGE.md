# Architecture execution coverage — rc36

Implementation date: **21 October 2026**. The retained primary-source review dates are stated below. This document describes executable interpretation coverage, not a certification of a customer's design or a benchmark result.

## What this release adds

The shared architecture reading can now check one **saved business contract, its provider-owned effect and its explicitly named runtime path and environment** across three distinct obligations: retaining a committed delivery intent, protecting the effect from repeated attempts, and discovering the authoritative business result. It uses the existing three-valued applicability evaluator. Unknown facts produce questions; contrary declarations produce a scoped issue; consistent declarations remain unverified.

The facts live in the existing Chapter 8 contract as `execution`, alongside its existing version, correlation key, idempotency key and dictionary exchanges. The environment and path are existing Chapter 10 records. The native Behaviour editor, change preview, concurrent-edit review, JSON round trip and Markdown export retain these declarations. No second decision store or alternative source registry is introduced.

The existing delivery comparison now prepares a distinct **business delivery agreement** between the business authority and effect owner. It copies only facts established by the reviewed option and answers. Environment, identity, changed-intent handling, uncertain-response semantics and business-completion discovery remain questions until explicitly supplied. Existing queue and relay transport-hop contracts remain separate: the producer's local atomic commit is not assigned to a transport intermediary.

The derived reading is available to the same chapter/Companion/provider path as other contextual insights. Every conclusion depends on the exact saved requirements, architecture drivers, applicable constraints, contract, participants, dictionary, path, environment and method receipt. A bounded provider packet may include the whole supported bundle or withhold it; it cannot keep the conclusion after removing a required source.

rc33 extends this same agreement with optional caller retry and circuit declarations. For a bounded synchronous request, the maximum attempt count (including the first), maximum complete attempt duration and total delay must fit the explicitly stated caller budget. The check also reads failure eligibility, retry ownership and open-circuit behavior together with repeat protection and uncertain outcomes. It does not infer a numerical target from unstructured requirement prose, or treat a declared limit as a measurement. This remains one source-pinned method and native contract, not a separate timing engine.

rc34 extends the same model to **one explicitly linked status request or result event**. The submission names its result contract, operation-identity relationship, outcome meaning and exact business-state field. The result uses the existing versioned contract, dictionary, authority and runtime records. The evaluator distinguishes submission acceptance from authoritative completion and checks both boundaries together. It follows no further result link; arbitrary sagas remain outside this interpretation.

The native Behaviour form exposes this in an optional disclosure. Suggestions use the linked contract's response or event dictionary and never overwrite authored field text. A question or validation remedy opens the exact linked boundary or authority field. Dictionary-shape and runtime questions open their existing native record. Saved Sol options can carry these same typed references between related drafts, preserving the submission's other execution declarations. The accepted link is visible in the model and the current SDD reading.

rc35 connects that result agreement to **one accepted read design**. The optional `outcomeReadTaskId`, `outcomeFreshness` and `outcomeMaxAgeSeconds` fields state the exact design and the consumer's required freshness. The read task retains its authoritative dictionary, approach, placement, age policy and verification duties. The interpretation checks caller, result authority, exact result-state dictionary, accepted approach and current source basis before comparing the declared ages. It does not copy a second cache policy onto the contract.

rc36 composes **explicitly linked execution journeys** through the existing `execution.invocationParentId` and `outcomeContractId` references. A caller link states that one request waits for another; names, process sequence and similar keys never create that link. The bounded traversal reads up to twelve declared contracts, their exact environments/paths, participants, dictionaries, linked accepted-read support and process mappings. It checks nested waiting envelopes, finite declared attempt exposure, shared-result authority and identity, cycles, missing links and omitted boundaries. Each business effect retains its own operation identity. Unknown retry ownership, unmodelled orchestration or an exceeded traversal bound prevents a fabricated finite result.

The same journey finding appears once in native Validate, contextual guidance and the SDD. Shared prerequisite questions consolidate only identical native object/field targets and show the dependent checks. Their action opens the existing exact field or dictionary editor. Provider context retains the entire deduction and required source set or withholds that deduction within the existing 22-source / 28,000-character allowance.

## Executable composition and its limits

| Declared condition | Executable reading | What remains to be verified |
| --- | --- | --- |
| Every committed change must remain deliverable | This retained-intent recipe requires one atomic boundary for the business change and publication intent. Separate commit/publication is a recorded loss-window issue. | Actual transaction boundaries, crash recovery, relay retention, replay limits and permitted loss. Other delivery designs need a separate interpretation. |
| Retry or redelivery is possible | The effect must be intrinsically idempotent or protected atomically with its duplicate record. Transport-only deduplication does not establish protection of the separate effect. | Implementation, restart behavior, duplicate retention, concurrency and effect count. |
| Duplicate-record protection is selected | Require a stable operation identity, a named request-dictionary key, changed-intent rejection and the effect-owning provider. | Real key scope, key retention, atomicity, semantic parameter comparison and concurrent requests. |
| A response may be missing | Retain an unresolved outcome rather than declare success or business failure from the missing response. | Time limits, actual recovery behavior and the customer's treatment of pending work. |
| The contract promises the business result | Require a request-dictionary correlation identity and an explicit authoritative status, correlated result or owned reconciliation contract at the provider. | Authentication, result retention, terminal-state meaning, inaccessible outcomes and reconciliation operation. |
| The contract promises acceptance only | Do not invent an additional business-completion promise. | Whether acceptance alone actually satisfies the linked customer requirement. |
| A separate status request or result event is explicitly linked | Check discovery style, caller/authority direction, result-contract version, same named environment and exact saved runtime path. Missing discovery stays unknown for both styles. | Actual endpoint or event behavior, authorization, inaccessible results and the customer's pending-state policy. |
| The result identifies the original business operation | Require an explicit same-operation declaration and compatible typed identity fields in the original request and result payload; a status query also carries that identity. Different field names are allowed when explicitly mapped. | Real mapping, tenant isolation, parameter meaning, identifier retention and handling of duplicate or late events. Matching names alone do not establish identity. |
| The result dictionary declares the business state | Check the exact field and that the dictionary's authority matches the named result authority. Acceptance-only meaning conflicts with a business-completion promise. | State transitions, terminal-state semantics, retention, query/event authorization and implementation evidence. Field existence alone does not prove those semantics. |
| A status result names an accepted read design | Require an accepted direct-read or cache-aside recipe with current drivers/method support, the original caller, named result authority and exact dictionary containing the business-state field. | A result event, another read pattern or another information scope requires its own interpretation. Actual read behavior and access control still need evidence. |
| A result requires the latest committed state | The accepted cache-aside or explicitly bounded-read recipe cannot establish that requirement. A declared strict authoritative read remains conditionally consistent. | Source consistency, concurrent commits, invalidation/refill races and returned versions. Direct access alone does not prove latest-committed behavior. |
| A result permits an explicitly bounded older value | Compare the accepted read design's declared source-value age with the consumer's numeric limit. For example, 30 seconds exceeds a 5-second requirement. Missing ages stay unknown. | Measured source-value age under load and failure, expiry/invalidation enforcement, cold-cache recovery and terminal-state correctness. A TTL is not automatically an achieved age guarantee. |
| The path/environment is missing, proposed or different | Keep the composition unknown. A route for another contract or environment cannot supply its evidence. | The actual placement, failure domains, deployment configuration and behavior. |
| A synchronous request declares bounded caller retries | Compare `attempts × complete-attempt duration + total retry delay` with the stated caller budget. Missing limits remain unknown; an overrun is a scoped conflict. | Full connection/request/response duration, back-off and jitter, cancellation, actual deadlines, aggregate load and the link from the stated caller budget to the customer's requirement. |
| Another layer retries outside the stated budget, or every failure is retried | Require one accounted retry owner and explicitly classified transient failures for this recipe. | SDK, proxy and downstream behavior, error classification and aggregate retry amplification. |
| A caller circuit is explicitly declared | Require an explicit request boundary and calls to stop through an open circuit while earlier business outcomes remain unresolved. This applies with or without automatic retry. A logical event or batch path alone does not identify the circuit's invocation dependency. | Real thresholds, state transitions, probe recovery, concurrent traffic and failure experiments. Choosing no circuit does not alone invalidate a bounded retry policy. |

The check is reusable for other business commands with the same declared semantics; it does not recognize a payment by its title or match the synthetic fixture. It does not prove distributed exactly-once execution, traverse an arbitrary multi-contract saga, execute a workload, establish measured latency/availability, or validate an implementation from policy prose. The caller calculation is an envelope of declared limits for one synchronous request; event redelivery, batch windows and arbitrary nested retry graphs need their own timing interpretation. A separate authority requires the explicit result contract supported above. Missing, proposed, dangling or wrong-environment result records cannot complete the reading.

The method identity is `AIW-EXECUTION-COMPOSITION-1`, interpretation version 6, defined in `public/composition-manifest.js`. `executionMethodSource` fingerprints that definition and supplies the precise primary-source identities. Source or interpretation withdrawal stops the inference without rewriting saved declarations or accepted proposal history. Earlier receipts remain historical and require current review. Version 4 added the explicit result-contract interpretation; version 5 adds its accepted-read/freshness composition. The authority is **an AIW implementation author's bounded interpretation of inspected primary sources**. It is not an independently approved project claim and does not promote any repository candidate.

## Coverage across the original six question families

| Family | Executable coverage already present and retained | rc32–rc33 behavior | Remaining coverage boundary |
| --- | --- | --- | --- |
| Cache / Redis | The native read method compares read approaches from the actual freshness, reuse and origin-load contract. Product readings require an explicit disposable-cache role, cache correctness/recovery contract, memory behavior and version; Sentinel and persistence have separate configuration gates. | Existing predicates and specialized read calculations remain intact. | No blanket Redis selection or inferred hit rate. Full version/edition matrices, cold-start measurements, invalidation implementation and resource measurements still require scoped evidence. |
| PostgreSQL / MySQL | Persistence methods compare invariant and transaction boundaries; product traits require declared engines, constraints, atomic key/effect behavior, topology and feature requirements. Hard constraints remain separate from preference weights. | The inspected PostgreSQL 18.x unique-key, row-policy and materialized-view interpretations, and MySQL 8.4.x unique-key/materialized-view-gap interpretations, now derive major/minor family from the actual option version. Patch versions in those families are accepted; missing versions remain unknown; other families withhold that mechanism reading. | These family gates do not reject an entire product. Compatibility tests, engine-specific error handling, isolation, locking and other versions need their own supported interpretation. Database selection is not reduced to a feature count. |
| Sharding | `composition-partitioning-1` independently evaluates capacity/locality/isolation motivation, local transaction assumptions, routing ownership, key skew, cross-partition reads, movement and recovery obligations. It preserves the simpler single-store alternative. | Existing specialized evaluation and reviewed placement are retained. | No automatic shard recommendation from aggregate read traffic or a product name. Distributed transaction designs, measured hot-key limits and operational recovery evidence remain explicit work. |
| Queue / durable delivery | `composition-delivery-1` compares direct, asynchronous and transactional-outbox approaches using explicit delivery, commit-scope, duplicate, ordering and replay conditions. | A reviewed business contract now connects the selected delivery approach to the reusable contract/path/environment composition described above. | Broker durability, acknowledgement or deduplication alone cannot prove the business effect or business result. Queue/stream versions and provider-specific guarantees are not exhaustively modeled. |
| Reverse proxy / load balancer | `composition-distribution-1` separates policy forwarding from backend selection; supports combined roles, state movement, health/readiness and independent work. Product configuration declares the actual proxy/pool role. | Existing role and configuration checks retained. | No universal either/or choice or forced two-product deployment. Edition-specific health behavior, network configuration and measured failover require additional evidence. |
| Circuit breaker / retry / isolation | `composition-resilience-1` retains caller-bound placement, bounded-call alternatives, failure exposure, timeout/retry/circuit policies and resource isolation obligations. | The contract composition also checks a declared attempt/delay envelope, eligible failures, accounted retry ownership and open-circuit behavior against the same repeat/outcome declarations. Accepted obligations retain exact native verification links. | Declared policy and timing bounds do not prove latency, recovery or availability. Explicitly linked nested requests have a bounded consistency and attempt-exposure reading. Arbitrary orchestration, omitted boundaries, measured overload/fault experiments and wider cross-pattern combinations need further coverage. |

All six families continue using their existing specialized evaluators. The new composition uses the shared applicability predicates; it does not replace those evaluators with a second inference engine. Repository descriptive relations remain discovery leads. Only eligible reviewed typed rules can support their own scoped applicability reading.

## Verification and immutability

The canonical obligation projection derives its current verification from explicit native delivery-action links and exact current confirmed evidence-source revisions. It never matches actions by title. The accepted solution and its original receipt remain unchanged. A changed supporting fact, source interpretation or evidence revision reopens review; recording verification does not turn a declared product capacity into a measured one.

The shared architecture insight carries current action sources and evidence revisions. “Current verification recorded” means that the linked reviewer record is current for its basis, not that AIW independently ran or certified a test.

Linked-result currentness includes both contracts, payload dictionaries, the authority, both runtime paths and the named environment. It also includes the requirements, drivers and constraints scoped to the result contract. A boundary's own requirement keeps its associated drivers even when its endpoint components supply additional context. Selecting the result contract exposes the related submission reading. Excluding any required source, or exceeding the bounded packet allowance, withholds the complete deduction instead of retaining an unsupported conclusion.

When the result names a read design, the full canonical requirement basis and architecture context also participate in native review and intelligence currentness. The provider's compact accepted-task source carries the actual inference operands and every dependency identity; its stamp still reads the full basis. Excluding a currentness-only dependency withholds that task source and its deduction. Read answers, accepted placement, exact authority/data/caller records and the method remain explicit supporting facts. This separates repeated context from inference evidence without weakening source exclusion or changing the 22-source/28,000-character limits. Explicit architecture-task queries retain the complete alternatives comparison within its separate 20,000-character allowance; repeated scope paths are pooled losslessly and decoded exactly.

The main SDD now projects the same accepted obligations and current verification as component specifications and delivery actions. It names the decision, requirements, drivers, target components, required evidence and review state. A scoped export uses the supplied component targets, and stale supporting sources remain visibly stale.

The rc35 read/result and driver-led journey suites cover native acceptance, exact repair focus, numeric preservation, stricter freshness, unknown/missing/wrong read scope, changed drivers and method support, source-policy exclusion, full provider packet closure, scoped SDD duties and reversal history. The two authored journeys use order fulfilment and payment with different read/product choices. The real workload verification step stays open.

The rc34 suites `outcome-contract-validate.mjs`, `outcome-context-validate.mjs`, `outcome-contract-ui-validate.mjs` and `outcome-design-journey-validate.mjs` exercise payment and order-fulfilment scenarios, exact native field routing, optional form disclosures, retained authored text, source closure, saved-option coordinated drafts, combined impact, acceptance, model and SDD projection, changed-source review and reversal. They use authored synthetic scenarios and in-process/DOM checks; they are not a live-provider quality or customer workload measurement.

The focused synthetic checks are in `execution-composition-validate.mjs`, `execution-composition-fixtures.mjs`, `caller-resilience-validate.mjs` and `caller-resilience-ui-validate.mjs`. They cover positive and contrary declarations, unknowns, exact path/environment scope, dictionary keys, native patch/clear/reload behavior, overlap-safe impact review, method withdrawal, bounded source dependency closure, native outbox prepare/accept/refinement, immutable adoption history, scoped constraints and product-family counterfactuals. Caller cases include equality at the exact budget, overrun, explicit zero delay, invalid numbers, no-retry/no-circuit choices and original native form → impact → edit → reviewed acceptance. The Happy DOM harness restores authored selected-option attributes to account for its parser limitation; this is explicitly recorded in the test and is not production behavior. These checks make no claim about live model quality or production payment behavior. Provider and delivery-evidence evaluation are separate native verification suites.
