# Guided contracts and payloads

The next increment extends the existing Chapter 8 Sol workflow. It begins with an inherited or saved contract and a requirement already traced through its participants. It reuses the application's boundaries and interaction style; it does not create a competing studio or repeat the application-design task.

## Delivered behavior

- Four compact steps: exchange agreement; payload and authority; repetition and uncertainty; protection and compatibility.
- Saved contract wording is carried into the task. A selected existing dictionary is reused without changing its authority, fields or lifecycle.
- A new dictionary can be proposed with a named owner, authority, classification, protection/lifecycle obligations and an explicitly described stable key. Its additional business fields are completed in the existing dictionary editor. The initial key is not presented as a complete business schema.
- Correlation and repeat-key names must exist in the request/event payload. Conflicting definitions of the same payload field block preview.
- Contract and dictionary share the established ghost preview, linked-impact review and explicit whole-proposal acceptance. Editing returns to the same Sol task. The saved alternative is available in Mind Factory.
- Working inputs, DES/ALT references, rationale and acceptance use the existing task, alternative, Changes and SDD stores. No new persistence subsystem or navigation section was added.
- Source snapshots include the requirement, drivers, decisions, contract, dictionary, participating systems and mapped logical responsibilities. Changes require source review. Acceptance establishes the reviewed contract as the task's current source while retaining the earlier basis.
- New timing and retention numbers are not invented, provider agreement is not inferred, and chapter checks/governance remain separate.
- The Chapter 8 reference tactic now derives suggested reference keys from the chosen contract's dictionary. An unrelated blank project no longer receives a payment-specific fallback key.

## Verification

The domain checks cover a reference request with a reused dictionary and a blank equipment-reservation event with a new dictionary. They verify source grounding, stable-key validation, no banking leakage, joint acceptance, unchanged reused definitions, source revision review, private object storage, owner isolation, optimistic conflicts, failed-write preservation and immutable SDD baselines.

The actual entry/editor/store/Worker DOM checks exercise both flows, including partial save/reload/resume, joint ghosts, returning to Sol, refreshing the common impact preview, acceptance, retained reasoning, Mind Factory and restoration of native chapter actions. Existing Chapter 4–7 guided design, interface impact, model-alternative UI, interfaces domain and final-review tests are retained and rerun.

Browser layout inspection is **not complete**: the sanctioned preview browser again timed out while refreshing its tab list, before opening a page. DOM checks are behavioral checks and are not reported as desktop/mobile visual verification.

Primary checks: `exchange-design-validate.mjs` and `exchange-task-ui-validate.mjs` (also with `AIW_BLANK=1`).
