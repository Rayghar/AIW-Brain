## Durable alternatives with comparable assumptions

A saved alternative holds up to twenty coordinated native commands across its applicable components, contracts, protection, runtime and technology specifications. The current architecture remains the comparison basis until the architect reviews and accepts an alternative through the established change flow.

Two to six draft alternatives can be compared under one named workload and scope. Capacity uses the proposed runtime plan's declared active placements, explicit per-replica and downstream rates, growth and failed replicas. Cost uses the proposed technology realizations' recurring costs, a shared currency and horizon, and explicit upfront, migration and exit costs. The result retains its inputs, evidence basis, limitations and alternative revisions.

Missing cost/rate evidence, incompatible units/currencies and overlapping concurrent edits are visible as unassessed or conflicting. A change to the base design or to any named alternative makes the recorded comparison historical. Revising an alternative and resolving conflicts refreshes its exact snapshots without overwriting unrelated work. No live vendor pricing, workload execution, automatic currency conversion or latency/availability proof is inferred.

## Knowledge that names its coverage

The repository stays the governed source/interpretation/review/release system. Its concept Evidence posture distinguishes descriptive catalogue material, exact implemented comparison families and eligible reviewed structured claims. Version, deployment, tier and configuration conditions remain visible. Candidates, withdrawn claims, changed sources and unrelated concepts cannot become executable support merely because their names match a prompt.

When the external repository service is unavailable, the same Sources search can read the exact current originals already retained by this project. Search results name this scope, source identity, original hash and line bounds; current project originals are not presented as the entire external repository corpus. Search neither promotes a claim nor changes the project. Superseded, withdrawn or hash-mismatched originals are withheld. Delayed responses cannot replace a newer search, reopen a closed reader or cross into another project.

The hosted fallback does not deploy or import the complete external corpus. Its acquisition, licence and governed review requirements continue to apply.

## External source reconciliation

A model source's revision action reviews explicit mappings from stable external element/relationship identifiers to native AIW records. The comparison preserves the last accepted foreign value and local value, compares them with the current local design and incoming source, and requires a choice for conflicting changes.

Relationship endpoint changes resolve through those reviewed identities. Names, parser order and generated placeholder IDs cannot silently identify an existing object. Missing or duplicate foreign identities remain explicit; removal does not automatically delete the local architecture. Unmapped source additions remain available for identity review instead of creating guessed native semantics.

Accepted changes pass through the existing canonical commands, project revision check, change journal and authenticated authorship. The original source text and revision trail remain retained. Repeating the same source bytes does not create another source revision. A stale preview or incomplete conflict choice is rejected atomically.

## Shared enterprise identity and impact

The organisation library's existing reviewed release can describe a shared service, API, data platform or enterprise capability. Its typed contract includes ownership, version, lifecycle, boundary, interface reference and failure domain. Release integrity covers the relevant source, applicability, limitations and lifecycle obligations.

A project adopts that signed release and declares a dependency from an authored native consumer, with its environment, relied-on contract, scope and criticality. The usage trail retains the shared identity and exact release. The model has one derived shared-service identity with per-consumer edges; different pinned versions remain visible per dependency.

Cross-project impact lists only projects the reader owns or has explicit access to. Organisation membership does not expose another member's private project. Contract/source changes, withdrawal, retirement or changed consuming definitions require review. Removed service metadata cannot remain as an accidentally inherited asset. These are declared dependencies, not discovered runtime connections, health checks or capacity reservations.
