## 1. Doctrine

AIW is a governed hybrid architecture-intelligence platform with this authority chain: policy, then approved knowledge, then deterministic reasoning, then a human decision, then an audited commit to the canonical graph. Proposers may interpret, propose, compare, critique and explain. Proposers are LLMs, Sol's drafts, imports and agent accounts. Only signed-in persons may accept, approve, release, waive, confirm, keep or promote anything, and a second person's step needs two different persons. No build approves an architecture decision, overrides a hard constraint, waives policy, promotes knowledge, silently changes the canonical graph, invents evidence or claims production acceptance: `productionAccepted` stays false unless every mandatory gate genuinely passes. No build impersonates licence counsel, an independent architecture reviewer, a four-eyes knowledge approver, an enterprise KMS authority or a production acceptance authority. Their true status is recorded as it is: counsel not engaged, approver not assigned, review not started, acceptance authority not established [plan 5, C]. Candidate and discovery knowledge is inert: it never affects a score, a hard constraint, an eligibility gate, a check or conformance. Every authoritative claim traces to an immutable source passage. There is one canonical Design Graph and one Brain execution entry point, and tenant and project boundaries hold. Work from source files, never from dist. Never run an old and a new authority path side by side: migrate, adapt and retire the old path. Never weaken security or governance to make a test pass.

## 2. How a build is done

1. **Start.** Inspect the branch and the working tree. Branch from the base the lead names, and merge `rc44/integration` first when the lead says so. Make a baseline checkpoint commit and record the plan in the notes [AGENTS.md; preambles of L, M, V, X].
2. **Tests first.** Write each case first and see it fail on the base before you change anything ("a case that fails today"). A case for a person's or a second person's step goes through the server (the command route), not only through a domain function [preambles of P, Q, X, Z]. In the fix-up, each must-fix item gets a case that is seen to fail first [plan 3, plan 4, AA1].
3. **Never loosen an assertion.** Replace an existing assertion only with one at least as strict, recorded as old -> new in the commit and the notes, naming the ruling or the lead's leave that allows it. No assertion is inverted. If the change cannot be built without loosening one, report that instead [J11, M5, U4, AA1].
4. **Old documents read byte-identically.** Create every new key only when it is first written. A document with none of the new records reads the same with and without the package registered: graph, trails, findings, stamps, fingerprints and SDD text. Compare against goldens captured from an unchanged checkout of the base (`node rc44-s0-readings.mjs --capture <sha>`), changing test files only, and never recapture an existing golden to absorb a change. Suites read no clock: every fixture takes a fixed time and states that it reads none. When old documents of some kind do take new stamps at their first read, the merge evidence says which documents and why [plan 2.7, plan 4 test 6, L10, Q7, X5(g), Y2, S0c].
5. **Resumable work.** The usage limit interrupts builds, so commit work in progress on your branch in coherent commits with no secrets, and keep `audit/rc44/build-notes/<build>.md` current. The notes hold: the plan; each case with the failure seen; deviations; the retirement list (J6); the "next" items (B10); the logged should-fix items and design concerns (AA1); which shared sentence comes from where (M7); "opens with records" and the route bytes (D10, AA2); every unresolved external dependency [plan 2.8, AGENTS.md].
6. **Attribution.** End every commit message with the `Co-Authored-By:` and `Claude-Session:` lines that your own session's system reminder gives, word for word. End every PR description with the lines it gives for PRs [brief].
7. **Size check, once per merge (owner, AA2).** The chapters route stays under the cap of **3,266,560 B** (raised by 32 KB from 3,233,792 B). Script files stay at or under the gate in `client-bundle.mjs`: 148 in the plan; S0-D10 may take it to the plan's 150, recorded there [Y1]; going beyond 150 is the owner's decision. The stylesheet (CSS) cap is unchanged, so new surfaces reuse existing classes [plan 2.4]. Each build reports its route bytes before (base) and after (head), from `node build.mjs`. The size evidence says what was measured and records the command that produced each figure, so the lead can repeat it [L9, V4].
   Per-slice byte booking is retired: allowances, the shared pool, `lead-bookings-size.json`, `routeBookings`, `assertBookingsAddUp` and S0's block "O1 the bookings add up". Reading AA2 with J11 (no ruling says it in these words): a size case written for the bookings is replaced by this check, recorded old -> new and naming AA2, like every changed assertion. The files-under-10-KB bucket is read as a ceiling: at most the gate, and at most the base's count plus the files the build adds [P8, R4].
8. **Review and merge (owner, AA1).** Each build gets one adversarial review by a separate agent, who challenges the design as well as the code [plan 1, plan 3], and one fix-up. Must-fix items are fixed in the fix-up, each with a case seen to fail first. Should-fix items and design concerns are logged in the build notes for later builds; they are not re-verified in further rounds. The lead merges after the fix-up, with a rebuild, the related suites and S0's suite. Every other rule stands: tests first, no assertion loosened, the second-person rule, candidate knowledge inert, `productionAccepted` false. A full regression closes each wave, including the browser run [plan 3, K5].
9. **Before handing back.** Do a clean install and a build. Run the build's own suites, the related suites and S0's suite, plus the browser suite where a surface changed. Inspect the evidence and review the whole diff. State every unresolved external dependency honestly [AGENTS.md].

## 3. General rules every package inherits

### Registration: what is registered, and what is edited
1. A package registers once, with `registerExtension({id, …})`, from its own modules. To register, it adds exactly three things outside them: one import line in `design-packages.js`, one route stub `<id>-route` (`needs`, `load`) in `public/design-package-routes.js`, and its suite `test:rc44-…` in `package.json`. The server registers every package at start and checks each; one that does not conform stops the server, naming every problem [plan 4, S0c, A2, D8].
2. The registered rows are the parts in the S0c table: `objectTypes`, `prefixes`, `records`, `layers`/`hops`, `checks`, `commands`, `track`/`trackPaths`, `lifecycle`, `canRestore`, `quietProposals`, `provenance`, `designKeys`/`evidenceKeys`, `design`, `upgrade`/`upgradeNote`, `sections`, `needs`/`load`. Anything else a package needs is an edit of built-in code ("What the registry does not carry"), made by the package inside its own build. Where a ruling changes S0, that build may edit S0's files for that row only [S0c, D7.7, J preamble, L1, L10, M2].
3. An extension only adds. It never replaces or wraps a built-in command, relation, check or text. A type that a built-in handler takes is never a package's. A section is placed after an anchor heading, stays inside the section it follows (no heading at or above its anchor's level) and never replaces built-in text; a heading another package prints is never an anchor. The workbench never imports a package: a package's text reaches the SDD through `sections` or its finding. Registration is idempotent by id, readers sort packages by id, and the registry holds no project state [plan 4, D3, D7.7, U5, S0c].
4. The lead assigns ids, and they follow dependency: a package whose records another package binds, measures or reads comes first. Under D8, `p10-knowledge`, `p30-deployment`, `p40-adoption` and `p50-workload` are assigned; the rest are provisional, confirmed or moved by the lead when the package's design is written. An id orders a package's layers, findings, sections and upgrade step. A hop's `from` is a built-in layer, an earlier layer of the same package or a layer of a package earlier by id. An id is fixed for good once its package's first slice merges [A2, D8, S0c].
5. State every collection a package writes, as `lifecycle` (a `container.list` path; a single-segment path is refused) or as `provenance.records`, with `provenance.nouns`: the boundary stamps the collections a package states as its own. A `second` type states `provenance.paths`. A key the workbench writes (`WORKBENCH_KEYS`) takes no lifecycle path, no `provenance.records` path and no evidence key. A provenance block on a package's command is not carried: the first package that needs one asks the lead for the row [D1, D3, D6.11, F6, H2, S0c].
6. A command answers the record it wrote as `selected` (several records as `selectedIds`), so that a batch restamps it. `created` is not part of the contract. `staged` is never combined with `person` or `second` [D7.3, L4, S0c].

### Emitter, trails and findings
7. With none of a package's records in a document, its emitter states nothing, no trail or spine moves, and every reading is byte-identical [plan 2.7, plan 4, D6.3].
8. State a relation only between objects, so ask `has(id)` before each `rel`. Emit no record under an id another record holds, and no relation from such a record. Never state a relation of a type a built-in hop reads between two built-in records. `add` may use a built-in type only when that type stands on no built-in layer (today `pattern`), and only from the package's own collection, with its prefix stated under `prefixes` [J2, J10, K9(c), D6.4, D7.2].
9. A hop onto a layer of a built-in type states `only`. A hop onto a built-in layer is refused, and so is a layer that holds a Chapter 1 type. A package's record explains a pair of built-in records only when no built-in chain does [D6.3, H1, K8, K11, S0c].
10. A finding marked `hard: true` (level `error`) is in the rc.10.73.42 non-waivable class, and nothing stricter. It takes no design-limitation, not-applicable or source-silent waiver, and the refusal reads: "“<title>” cannot be waived: change the design. Until then, fix it before review or carry it as an action." The dialog offers the other treatments and no waiver, and the finding blocks exactly as a built-in non-waivable finding does. `hard` is read only inside `nonWaivable()`, and `NON_WAIVABLE` stays frozen. A finding that must block a chapter's review or freeze is hard and gets no row of its own [A1, D11, M3, V2].
11. No finding before its surface exists. A finding about a step that no surface yet offers is held back until the surface is built. Until then the reading states the standing, and an upgraded old document gains no finding. A finding that can arise only after a person acted on this build may stand [J7, K4, X5(a)].
12. Finding ids are unique in the review: `<code>:<record id>`, with a code that no chapter and no other package uses. Checks answer `[]` for a document without the package's records, and they are pure and cheap. A list-11 finding shows exactly where the built-in list-11 findings show [D7.4, S0c].

### Person-only and second-person steps
13. Every new accept, approve, release, waive or acceptance step needs a second person (`second`, which is also person-only) [plan 2.5, D1]. A second person stands behind every person's word on a hard constraint (a row a person judged pass or fail, a row named unproven): a second-person step is taken before the decision can be accepted [Q4]. Every keep is a signed-in person's step, at any depth of a batch or an alternative [L1], and so is the step that confirms a record no person has stood behind [D1, F4]. A type ending `.review`, `.handoff` or `.intake` states `person` or `second` [D7.5]. A person-only step refuses an agent account, a draft by Sol, an import and a request with no signed-in actor [S0c, I1, X1].
14. A second person's step reuses `verifierRefusal` (`public/architecture-obligations.js`), applied to the record or to a projection `{id, actor, history, owner?}` that names everyone who wrote what the step covers, preparers included. The record keeps `actor` and a `history` entry `{revision, actor}` for every save. No package writes its own check. A projection may leave out a save only where the design says which saves, and it then needs one case with the save left in and one with it left out [plan 2.5, D7.1, J1, Z1, S0c].
15. Two persons. After `verifierRefusal`, the boundary also refuses unless a person other than the actor stands behind the record as it stands now: either its author stamp is a person's, or a person confirmed or kept it. One person accepting what only an agent account or a draft by Sol wrote counts as one person. An unstamped record has no person behind it. The refusal says what must happen first: a second signed-in person saves or confirms the record. A package with a `second` type therefore offers a person's confirm command, and names which of its person-only steps confirms a record that no person has stood behind [D1, D12, F4].
16. At read time a stored step is checked the same way. `apply` stores `{actor, at, account: author.account}` from what the boundary hands it. The reader calls `verifierRefusal(projection, step.actor, step.account)` and requires `account === 'person'` [D7.1].
17. A step taken in another project is no step here. A person's or second person's step is kept under the record's key `review`, which a template copy clears. An author stamp made before a template copy, a restore or a recovery import counts as no person's [F3, L5, Q6].
18. The undo of a person-only or second-person step is itself a person's step, by the account that saved it. `validate` is for what a type refuses by who writes the commit (a staged handler is not told the author in a batch). It is asked for the command sent on its own, for each command of its type in a batch, and for every command an alternative carries: when it is saved, when it is revised and when it is merged [D6.1, D6.2, S0c].
19. The boundary keeps author stamps current, not the package: every record of a package's own collections that a commit changed is restamped as that commit's. No record counts as authored on the strength of a keep that carries no person's stamp [H2, L1].

### Merges and preparers
20. A merged record is stamped as written by its preparer, with the author kind and actor the alternative recorded (a draft by Sol stays Sol's), and as reviewed by the merger (`author.mergedBy`, a review marked `merged`). While the merge's stamp stands, both the preparer and the merger are refused as the second person, and the preparer stays among the record's writers after any later edit. A merge is a person's review of the batch, which counts as a person standing behind the record (D1), but it confirms no record's words. A record merged before this build keeps its old reading [Y3, Z1, Z7].
21. An alternative with no list of preparers (saved before this build, carried from one, or imported) merges stamping nothing as anyone's, for built-in and package records alike, so its records fail closed. Its merge is refused when one of its commands confirms or keeps a record. The refusal names the command and its alternative, what it confirms or keeps, why, and what to do, and it writes nothing. A merge whose command would confirm what its own preparer wrote is refused (four eyes) in words to the merger: the command, its alternative and its preparer, and what to do (revise the alternative without the confirmation; another signed-in person confirms after the merge) [Z4, Z5, Z9].
22. A revision keeps a command's preparer only when the command equals the stored one or its rebased form. Otherwise the command is the reviser's, and the reviser's entry carries the earlier preparer's kind as `from` [Z3].
23. An event that a package's staged handler or its tracker adds inside a reviewed batch or a merge states no author fields; the boundary removes them. The SDD prints a merged record as merged by its merger and prepared by its preparer, not as confirmed. The review plan keeps listing a merged draft by Sol until a person confirms or keeps it [H3, Y3, Z7].

### Imports and template copies
24. A recovery import neutralises authority. Before any early return (including for a package without `finalReview`), it moves aside (`imported…`) every step, judgement, confirmation, choice and instantiation, and the authors of every alternative and history entry. What it moves aside counts as nobody's here, whatever its dates. It also clears the library mark. Suites with steps call `assertRecoveryClearsSteps` [G5, M2, Q6, Z2].
25. A template copy clears steps (`review`) and names only the packages whose records it keeps; a name this build does not register is copied as stored. A template row whose package upgrade is due is copied as the read would store it. Suites with steps call `assertTemplateCopyClearsSteps` [F3, K2, P2].

### Trackers: they journal what they change and confirm nothing
26. A package has one tracker, `track(prior, next, command, at)`. It is called after the built-in trackers, for every command and for each inner command. It returns at once for a document without the package's records, and it answers nothing (any answer is ignored). Every change it makes is part of the same commit, journalled as one change event with the record as its source [D4, F5, J5, O2].
27. A tracker mends content; it decides nothing and makes nothing. It states the built-in collections it mends as `trackPaths`, a map `{path: [fields]}`: built-in record collections only (in both `COLLECTIONS` and `RECORD_PATHS`; not the narrative, `finalReview.*`, `changes.*`, `workbench.*` or `members.*`; none twice). This is an allow-list checked at start (`TRACK_REFUSED_PATHS`, `trackFieldRefused`): no collection a chapter accepts or approves, no package's own collection, and no identity, revision, history, standing, status, governance, approval, recording, snapshot, confirmation or review field. The boundary puts back every unlisted field, moves `revision` forward by one only where a listed field changed, and stamps the change as the commit's. A call that adds or removes a record, or that moves the chapter's reading of a proposal, is refused (500 `fault`, naming the package) [O2, R1, R2, T1, T3].
28. A tracker changes no other built-in collection. Every suite whose package has a tracker calls `assertTrackerStaysInPaths` on its tracker's cases; wp2 does too, though it states no `trackPaths`. A record kept under two paths is one record to every tracker. What a bound record says to a tracker is its content, less the readings it keeps of others, the review flags a person sets on it and where it is drawn [K7, K10, O2, T3].

### Upgrades and stamps: an upgrade moves no stamp, and unstamped is not a person's
29. `upgrade(p)` is idempotent. It answers `p` itself, cheaply, when nothing is due, and otherwise a new document; it never changes the document it is handed. It works on a document that lacks any chapter. It mints no id that a record holds. The records it writes carry no author stamp [plan 4, K9(c), S0c].
30. A package's upgrade is stored only by the read that opens the project, with a recovery point. The one writer (`project-storage.js` `saveStoredProject`) refuses to store over a row whose package upgrade is due (409, "Reload the latest project"), for every route and every background job. No route needs a rule of its own [J8, K1, K11].
31. No person's or second person's step moves a design stamp, at any revision, and an upgrade moves no stamp of an old document (step 4 says how an exception is recorded). The design fingerprint never reads the `history`, `review`, `confirmed` or `provenance` of a package's record: state a `design` row that leaves them out; a statement is cheap and answers the same value for the same document. A record that restates what an earlier record still says leaves that out until the earlier record is retired. Suites call `assertStepsMoveNoStamp` [J3, L5, S0c].
32. A proposal says nothing to the design fingerprint. Generating or dismissing one moves no stamp or version and clears no check (`quietProposals`). Keeping one is a design change. The provenance counts and the review plan still read proposals [L6, M6, U4].
33. A package's record with no author stamp (written by an upgrade, or merged with no preparers) is counted on an SDD line of its own and never as written by a person [J9, Z5].
34. A document names a package (`workspace.packages`, written by the boundary; neither fingerprint reads it) exactly when it holds a record of that package; a document no package wrote into does not gain the key. A document that names a package this build lacks can still be read, but every writing route and every export (registers, SDD, ARS) is refused at one place (409 `missing_package`): a design this build cannot read in full is not changed, frozen or printed by it. Renaming, archiving, restoring from the archive and a recovery export stay possible. In the browser, `ensureExtensions` rejects, naming the package; a load that fails after a save is reported as saved and not yet shown, the store goes to `behind` (not `error`), and nothing says another tab changed the project [D2, F2, F5, P2].
35. Fail closed on what this build cannot read. A status this build does not write reads as one it does not read. A definition it cannot identify reads "not evaluated", never "current" [K3(b), K9(b)].

### No second truth
36. No second truth while the earlier path stands. Hold a new step back to the slice that moves its readers. Refuse the step while the earlier path's finding for the same design stands as an error. The notes keep a retirement list that names each earlier step and reader with the slice that retires it [J6, K3(a), L2, L9].
37. Retire the old path in the build that replaces it, and re-point its suites old -> new, at least as strict. The lead gives leave for each named suite. A suite red at the baseline runs at least as far as its baseline red line and stops there for the same reason, or passes [AGENTS.md, Q8, U2, U3, V5].
38. A shared reader's contract carries every caller. A build that changes what a shared reader answers changes every caller in the same build, with a case per caller [Q1].
39. A guard is one function at every door. A rule about how a record comes to stand or to read verified is one function, asked on every path that reaches that state, later paths included (imports, restores, organisation releases). It is asked before anything is written, so a refusal writes nothing. Later slices extend an existing reader and never write a second one [L2, S1, S6, S10, X3, Z9].

### Knowledge boundaries
40. Candidate knowledge is inert. No candidate or unreleased form reaches a check, an eligibility gate, a score or a conformance reading. Each package's suite proves this, including for a document that has candidates written straight into it [plan 2.6, B2].
41. Only the concept readers read a claim that carries a form. Decision-bearing content reaches a design record only through an active pin, and its facts are read from the released claim on every read, never from a stored copy [B1, E2, Q6].
42. Bound knowledge must be current. Released knowledge a record binds that is withdrawn or deactivated raises an error that refuses acceptance. A concept that is retired, or not eligible as a whole in the pinned release, hands over nothing and the reading says why. A server reader of pins refreshes the stored currency first or reads the currency computed on read [B5, J4, Q8, X5(c)].
43. Releases are whole, immutable copies that hold plain claims or forms, never both. The releaser is refused for every row they stand behind: as its author or last editor, as the confirmer of a row no person wrote, as the verifier of a row an import, a draft by Sol or an agent account wrote, and for the concept record itself. The refusal names the row and why; no row is dropped silently. The organisation receives only what the library stands behind now [E3, E4, P1, X2, X5(e)].
44. One id names one concept, and one alias names one concept in every scheme. Every path that makes a crosswalk row stand or read verified asks the shared `admit(document, conceptId, row)` and `oneAlias(document, row)`, which read the register and the active releases, identified by (project, row id). Bounds count what stands [P3, P4, S1, S2, S6, S10, X3].
45. A request from an agent account, as a draft by Sol, as an import, or stating no author is refused, wherever it is, when it would change a concept that was ever reviewed or is in a release (anything its hash covers, a form claim added or a topic remapped included) or lower its standing, or change a crosswalk row whose review stands. A person's request keeps today's fail-safe effect. The proof is a walk, not a list: every `knowledge.*` command type, sent by each kind of non-person, against a reviewed concept and a released, active one, leaves the concept's standing and what a pin hands over as they were; a command type added later joins the walk or the case fails [B3, E1, G2, I1, P5(d), P5(f)].
46. Concepts, topics and form claims are written only in a project that a person has marked as a knowledge library. Outside a library, `conceptTeachingForms` returns released content only. Until wp1 S6, the last build, is built, candidate teaching content is visible in the library project only; the owner's decision on showing it in design projects is pending until then [B2, Q11, AA4].
47. Every authoritative claim traces to an immutable source passage. A governed identity names the claim whose passage holds it, and every statement of a decision-bearing form rests on its own quote [AGENTS.md, B6, P7].
