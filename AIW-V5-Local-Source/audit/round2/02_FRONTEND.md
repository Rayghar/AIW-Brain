## 1. Summary

1. The client is 209 ES modules (8.5 MB in `public/`, 3 data/vendor files = 3.35 MB); 208 are reachable from `entry.js`, 3 are server-only or test-only files that live in `public/` by accident.
2. The save path has a new, measured defect: an ordinary edit opens a second modal ("Review this design change") on top of the editor while the editor reads "Saving…" with its buttons disabled; after the save completes, focus is dropped to `<body>` because the opener is destroyed by the full re-render.
3. Nothing is paged or virtualised: with 305 responsibilities the Chapter 4 Work tab renders 300 rows (4,296 elements), Validate 5,962 elements, the Model 3,502 elements with 1,263 SVG nodes; selecting one node costs 703 ms and a save re-render 389 ms of long tasks.
4. A CPU profile of the Chapter 7 Work→Model switch shows the remaining F-03 cost precisely: per-capability snapshot fingerprints (`technology-domain.js:10`, 82 ms self) and a pure-JS SHA-256 (`brain-integrity.js:6`, 27 ms) run on every render.
5. Helper duplication survived the html-escape consolidation: 87 byte-identical function groups (~28 KB), e.g. `list` in 38 files, `project()` in 15, `load()` in 12, `field()` in 27 files with 23 different bodies.
6. Two static import cycles (5 and 4 modules) and 6 dynamic cycles around `workbench-ui.js` remain; the domain/UI boundary itself is clean (no `-domain.js` touches DOM or window).
7. State: 21 `window.aiw*` globals (271 refs, 54 files) unchanged; one (`aiwDecisionContext`) is computed at boot on every Chapter 4–11 page and read by nothing; `project-store.command()` has no queue, so two in-flight commands produce a 409.
8. 142 `setTimeout` calls, 47 of them 30–80 ms "render after layout" waits in the chapter models; 14 empty `catch{}` (down from 73); 21 modules register document/window listeners at import time with 3 `removeEventListener` in the whole client.
9. Build: esbuild produces 110 chunks and one 622 KB stylesheet, no source maps, no size budget; the 1.77 MB catalogue chunk is reachable from 57 chunks. CSS: 4,623 hex literals (2,342 distinct) against 1,207 `var()` uses and 7 `:root` tokens; 386 `!important`; 26 classes with no reference at all.
10. Tests: 13 UI modules (99 KB) have no test reference; 34 of 117 suites rely on 291 fixed `waitForTimeout` sleeps; the baseline record shows browser suites take 645 of 802 CPU-seconds, and a full `release-checks.mjs` run started here hung with all three workers blocked by orphaned suite servers (F2-27).

## 5. Not verified

- Only Chromium (headless, 1440×900) in this container; no Firefox/Safari, no real network, no low-end device; every timing is a single run.
- The first full regression on the current code did not complete here (F2-27); a second run did (§3.4). Which three browser suites failed first in the hung run, and why (assertion vs. CPU contention from three concurrent Chromium suites), was not determined because the runner keeps a suite's output only until the run ends.
- The listener growth check covered tab and view switches within one page only; chapter changes reload the page, so cross-chapter accumulation cannot occur by construction and was not measured.
- Dead-CSS detection is textual: a class is "unreferenced" when no JS/HTML file contains its name as a whole token; 176 of the 202 unreferenced classes share a prefix with a dynamically built class name and may be live.
- The duplicate-helper extractor matches `function name(` and `const name = (...) =>` forms only; class methods and object-literal methods are not counted.
- Stale-closure detection is a heuristic (a `const p = project()` followed within 2,500 characters by an `await` on a save call and a later use of `p`); it found two sites and may miss others.
- The 300-object fixture was restored through `/api/recovery`, which bypasses the command validators; the counts it produced (405 objects, 1,180 relationships in the preview) are consistent, but the same load was not reproduced through the UI.
- Whether the unreachable `public/` modules are copied into the production `dist/client` was not checked (the bundler only follows `entry.js`; `build.mjs` was not inspected for extra copies).
- No screen reader was used; focus results are `document.activeElement` readings.
