## 1. Direct answers

**How the archive implemented Co-author.** Two layers. On the server, a "stage co-author" drafts typed field operations (append an objective, update a node property and so on) through an OpenAI-backed gateway with a deterministic fallback, records them as a durable Brain transaction, and applies them only after approval, a written rationale of at least 20 characters and a graph-freshness check. In the browser, a "generative cursor" lists chapter-derived proposals, previews the exact effect on the record, requires the person to review the values and give a reason, and then saves through the chapter's ordinary command. The cursor layer calls no model at all. Evidence and line references are in `06_ARCHIVE_ADOPTION.md` §2.

**How the archive implemented Ask Sol.** One governed endpoint, `POST /api/co-architect/ask`. A local deterministic kernel answers first; a model answer is then requested, schema-validated and grounded to a list of allowed reference ids, with the deterministic answer as fallback. The client companion has five jobs (Understand, Propose, Compare, Ask, Draft), context chips for the selected object, and turns an answer into a change only through explicit clicks: "Put this in <field>", a candidate disposition with rationale, or "Answer on the desk". `06_ARCHIVE_ADOPTION.md` §3.

**How the archive implemented the spark.** A click-only button in each field header ("SolPulse") opens Sol scoped to that field. Offers come from three deterministic sources: text rules over what the person already typed, a regex-ranked library with honesty labels (you said / analogue / confirm), and proposals distilled from the last Brain answer. Accepting writes the field in the browser draft with origin `sol-draft` and a ledger entry; the server sees the value only when the chapter is saved. The archive's own doctrine lists "auto-fill the chapter from related knowledge" under what it will not do; its only bulk fill is "populate empty Introduction fields from the person's own brief". `06_ARCHIVE_ADOPTION.md` §4.

**Can V5 adopt them.** Yes, in concept and in most mechanics, and V5 already owns the governed half: server-recorded intelligence runs with packet review, budgets and redaction; a field-draft contract for architecture tasks; per-record "knobs" that Sol may refine through change review; deterministic hints with a "Fill unanswered fields" button in guided design. What V5 lacks is a spark on ordinary chapter forms, an LLM field-draft mode for those forms, per-field provenance in the saved record, one suggestion list with accept, edit and dismiss, and acceptance telemetry. The React event model, the client-side canonical writes and the unlabelled bulk fill must not be copied. The adoption plan (`06` §6, `04` §4) keeps the authority chain intact: every suggestion is proposed, labelled by source, individually accepted by a person, and enters the document only through the chapter's own command carrying `solSuggestions` provenance that the server validates and stores.

**Making the spark useful for autofill.** The design has three bands, always in this order: *From your project* (deterministic, cited: the requirement, driver, decision or sibling record the value comes from), *Confirm* (a value the chapter guide or journey already implies, shown as a question), and *Sol draft* (a server-recorded model draft with its packet and run id). A per-form action "Fill empty fields from your project" fills only empty fields, only from the first band, and shows what it filled with an undo. Nothing is written silently, numeric fields are never drafted, and the stewards' view gets acceptance counts per field and source. First tranche: Chapter 4 purpose, boundary and owner; Chapter 8 contract policies; Chapter 9 threat and control; Chapter 10 runbook, recovery, monitoring, scaling and readiness. Effort: M for the shell, registry and provenance; M for the server field mode and popover; S for the remaining chapters; S for telemetry.

## 2. What each track found

**Backend (`01`).** Tenant and role boundaries hold under live probing. Two High findings: a restored package's imported review author satisfies the two-person approval rule (B2-01), and the local server buffers a whole request body before any size check, so a 200 MB POST took resident memory to 1.15 GB before being refused (B2-02). Also: every edit rewrites the whole change journal to a new blob that is never deleted and is embedded in every project read (B2-03), no retention job (B2-04), command payloads are typed only by `type` (B2-05), integrity faults answer as transient 503 (B2-06), blobs ignore `AIW_LOCAL_DB` (B2-07), viewers can bulk-export the whole project (B2-08), interrupted runs hold their token reservation for 24 h (B2-11), no health endpoint, shutdown handler or request timeouts (B2-13), and the packaged Worker embeds every asset in one 7 MB module while API JSON is never compressed (B2-15, B2-17).

**Frontend (`02`).** Four High findings, all measured: an ordinary edit opens a second "Review this design change" modal over the editor while the editor reads "Saving…" with its buttons disabled (F2-01); after a completed save focus drops to `<body>` because the opener is destroyed by the full re-render (F2-02); nothing is paged or virtualised, so a 305-responsibility project renders 300 rows on Work, 5,962 elements on Validate and 1,263 SVG nodes on Model, with a 703 ms selection and 389 ms of long tasks per save (F2-03); and the regression runner hangs forever when a browser suite dies without stopping the server it spawned, because the server inherits the runner's pipe, the runner resolves only on close and its timeout kills the suite's pid alone, which blocked all three workers during this audit (F2-27). The CPU profile names the remaining render cost: per-capability snapshot fingerprints and a pure-JS SHA-256 on every render (F2-04). Structure: 87 byte-identical helper groups (F2-09), two static import cycles (F2-08), 21 window globals with one computed at boot and read by nothing (F2-06, F2-26), an unserialised command path that yields 409 on two in-flight saves (F2-12), 142 timers of which 47 are layout waits (F2-14), 13 untested UI modules and 291 fixed sleeps in tests (F2-21), no source maps or size budget (F2-19), no linter (F2-20), and a nominal token layer with 4,623 hex literals (F2-18).

**Diagrams (`03`).** Every Model tab opens on one standard-notation Diagram that uses 13 of its 23 defined element kinds, one line style and one arrowhead for every relationship, and two labels that point against ArchiMate direction. Routing does what the README says it does not: on the reference project connectors cross elements 35 times in Chapter 7; on a 49-element project the grouped picture has 608 crossings and the tree is 6,234 px tall. The same object has four palettes and four vocabularies across the Diagram, the chapter map, the explorer, the anatomy and the SDD atlas; the SDD HTML draws its own figures from a different model builder; the PDF and DOCX carry no figures; exports carry no hash manifest. Twelve ranked enrichment proposals: a notation kit with distinct line styles and cardinality (P1), an in-house Sugiyama layout with crossing minimisation and channel routing (P2), one shared SVG renderer with a hashed export manifest (P3), a viewpoint catalogue (P4), annotations (P5), baseline diff (P6), a vitals overlay (P7), process notation for Chapter 2 flows (P8), Structurizr, PlantUML, Mermaid and draw.io exports (P9), accessibility of the picture itself (P10), "Sol explains this picture" (P11) and persisted pins (P12).

**Brain (`04`).** The Brain is a well-governed pull machine with almost no push: on 40 of 45 pages Sol's judgement needs a click. High findings: on Work, Validate and Output of Chapters 5–11 the Sol panel speaks about LR-001, a Chapter 4 record, because the shell's default selection is carried across chapters (I2-01); Chapter 1 requirements, Chapter 11 and every drawn element have no reasoning path (I2-02); nothing proactive appears per tab (I2-03). Two Sol pipelines coexist with different retrieval, limits and validators (I2-08); Mind Factory shows the same sketch on every page of Chapters 2–7 and only six patterns have relevance rules (I2-06, I2-07); hover explanations are two unrelated mechanisms (I2-11); editors have no field-level suggestion at all (I2-12); there is no prompt pinning, no per-field acceptance statistics and the only evaluation evidence is a mock-provider run (I2-16 to I2-19); the name Sol is put on rule-based menus and template text (I2-04, I2-05, I2-21); the catalogue loads on Chapters 1–3 despite the comment saying otherwise (I2-20).

**UI/UX (`05`).** **UI/UX (`05`).** Six High findings from seven scripted task flows and a 45-page sweep at desktop, tablet and phone widths. The product is still four page applications (Chapters 1, 2, 3 and 4–11), so every third chapter change is a full reload that loses the working tab and drops the project from the URL, and the two shells differ in 23 visible ways (U2-01). The object companion is beside the stage in Chapters 4–5 and below it in Chapters 6–11, at the end of Validate pages up to 13,700 px tall (U2-02, U2-03). **Archive (`06`).** See §1. Those are reasons to adopt the design, not the code.

## 3. Cross-cutting themes

1. **One object, many voices.** The same record is described by the Diagram, the chapter map, the explorer, the anatomy, the SDD atlas, the hover tip, Sol's panel and the Mind Factory sketch, each with its own palette, vocabulary and selection state. The I2-01 bug is the sharpest symptom: the selection that drives Sol is not the selection the person is looking at. A single selection and vocabulary model (the record id plus chapter and tab, resolved once) would fix I2-01, D2-07, I2-11 and several UX findings together.
2. **Pull, not push.** Sol, the Mind Factory, hover, the spark and the guide are all one click away and never volunteer; the proactive surfaces that exist (milestones, readiness, desk drafts) are rule-based and labelled. The field spark and per-tab briefs are the cheapest way to make the intelligence visible on every page without weakening the authority chain.
3. **Scale was never a fixture.** Every list, model and validate view renders everything; every save re-renders the shell; every edit rewrites the journal blob. A 300-object project is usable but visibly slow on the client and grows the server document on every edit. A 300-object fixture belongs in the browser gates.
4. **Honesty labels are mostly right and occasionally wrong.** The product is careful to say "rule based" and "no language model is connected", yet it puts the name Sol on template text, says "publish to apply" on a local server, and claims in a comment that the catalogue is not loaded where it is.
5. **The governed half is done; the ergonomic half is not.** Runs, packets, budgets, redaction, adoption, receipts, four-eyes review and change review all exist and hold. What is missing is the last metre to the person: a spark on the field, a draft that lands in the form, a suggestion list with reasons, and evidence that people accept what Sol proposes.

## 5. Doctrine check on the proposals

- No proposal lets a model approve, override a hard constraint, waive policy, promote knowledge or write the canonical graph. The spark and co-author designs route every accepted value through the chapter command a person submits, with provenance the server validates.
- Candidate and discovery knowledge stays out of scoring: the spark's catalogue band carries labels and no scores, and the reasoning packet already excludes unreleased claims.
- `productionAccepted` is untouched by everything here; the evaluation item in P2 needs a real model run and a human reading of it, which this round could not produce.
- The four-eyes weakening in B2-01 is a defect in the existing product, not in a proposal; it is the first item on the roadmap.

## 6. Not verified in this round

- No model was connected; live answer quality, latency and cost are unmeasured.
- One browser (Chromium headless) at one viewport, plus a phone-width pass in the UI/UX track; no screen reader, no real users.
- Timings are single runs on a shared container. The full regression started during the frontend audit hung on orphaned suite servers (F2-27) and was stopped without a report; a second run after the audit passed all 114 suites in 346 s wall at 3 workers (`02` §3.4). No code changed in this round.
- Screenshots, sweep JSON, probe scripts and the 300-object fixture stay in the session scratchpad and are not committed; each document names the script that produced its numbers.
- Nothing in this round asserts licence, legal, independent-review, KMS or production acceptance status; those authorities remain external and unrecorded.
