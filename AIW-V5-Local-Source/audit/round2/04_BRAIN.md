## 1. Summary

1. The Brain is one well-governed **pull** machine and almost no **push**: on 40 of 45 pages the only way to get Sol's judgement is to open the panel or select a record and click *Ask Sol to assess it*; what appears without a click is rule-based (next-milestone strip, readiness tiles, "What the model shows", Sol's round list, desk drafts) and is mostly labelled as such.
2. With no model connected the panel still opens on 42 pages and says what Sol *would* read, but every page's Sol content on Work/Validate/Output in Chapters 5–11 is about **LR-001, a Chapter 4 record** (the studio's default selection carried across chapters), so "Sol reads Chapter 4's reading of it" is shown on Chapter 8 Validate and Chapter 11 Output (I2-01).
3. Two implementations of "Sol" coexist: Chapters 1–3 have a rule-based action menu labelled "Sol · Act on this context" and template "ghost" proposals; Chapters 2–10 model records have the reasoning path (chapter reading → packet → two-pass LLM → refinements through change review); Chapters 1 requirements, Chapter 11 and every drawn (non-record) element have neither (I2-02, I2-03).
4. The reasoning packet is grounded and disclosed (record fields, chapter checks, desk vitals, drivers, playbook tactics, product mechanisms, governed and *learned* claims, each with posture and receipt, shown before sending); the older *generate* path is lexical retrieval with different limits, validators and a second implementation of the source check (I2-08).
5. The catalogue (666 records, AKR-0.10.73.5) reaches the user as descriptive concept cards found by word overlap and a Mind Factory sketch that is identical on every page of Chapters 2–7; only six patterns have relevance rules; pattern DNA (component/interface kits, obligations) is not used in reasoning, which is consistent with the doctrine but leaves Mind Factory generic (I2-06, I2-07).
6. Hover explanations are two unrelated things: the chapter models' own tooltip (record description, rule-based) and the legacy `#cursor-tip` whose Brain line is a count ("Architecture Brain · 0 reviewed claims in scope") (I2-11).
7. Editors have **no field-level suggestion or prefill at all** (verified by grep and by reading the eight `*-ui.js` forms); the only prefill mechanisms are guided design's "Fill unanswered fields with these values" and the Chapter 1–3 ghost proposals, both whole-record and deterministic (I2-12).
8. Adoption is honest: nothing Sol says enters the canonical document except through `intelligence.adopt` on a saved run or the chapter's own change review, and every assessment outcome is recorded (`SA-nnn`) and reaches the SDD; but there is no prompt/instruction pinning, no per-field acceptance statistics, and the only evaluation evidence is a mock-provider run (I2-16 to I2-19).
9. Labels are mostly honest ("Contextual guidance is rule based. No language model is connected."), but the name *Sol* is put on rule-based menus, on a deterministic "Sol's round", and on template text with bracketed placeholders; the generate composer says "publish to apply them … runtime settings" on a local server (I2-04, I2-05, I2-21).
10. Recommended order: fix the cross-chapter selection bug and the Model-tab entry (S); one Sol voice with three labelled bands (rule / draft / assessment) across the seven help surfaces (M); proactive per-tab briefs built from what already exists (M); field spark per §4 (M+M); learning-loop telemetry, prompt pinning and a real-model evaluation run (S+S+external).

## 4. Field-level spark for V5

The archive analysis `round2/archive-coauthor.md` §6.1 gives the port plan and §6.4 the per-form hook-point table (form ids, fields, deterministic and LLM sources for all ten chapters). This section does not repeat that table; it fixes the V5 design where it must meet the doctrine and the code found above, and names the starting fields.

### 4.1 Principle

A spark is an invitation on a field, never a writer. Three kinds of offer, in this order, each labelled: **From your project** (deterministic, cites the record it was copied from), **Confirm** (the chapter guide's question for this field, `public/chapter-guide.js:18`), **Sol draft** (a server-recorded LLM run, cited, source-checked, marked "draft — not saved"). Accepting an offer only fills the input in the open dialog; the value reaches the project through the chapter's ordinary command, which carries provenance. Numeric and typed fields (ids, minutes, ms, replicas, currency, selects) never get an LLM offer; deterministic offers may copy a recorded number only with its ref. Nothing is auto-answered; there is no bulk fill except an explicit reviewed list (as `public/design-task-ui.js:24` already does).

### 4.2 Data flow

```
field focus / spark click
  → field-spark.js: session {formId, field, recordId|null, parentId, current, offers[]}
  → offers[] = fieldSuggestions.suggest(formId, field, p, formValues)      (pure, client, ≤3, each {value, why, ref})
             + guideOffer(chapterGuide(p, ch, recordId).question)          (existing, rule-based)
             + [when connected] "Draft with Sol" → POST /api/intelligence/context {mode:'field', fieldDraft}
                                               → packet shown (sources, S-refs, omissions) → POST /generate
                                               → run stored (intelligence_runs + FILES) → result.fieldDraft[]
  → Accept: input.value = offer.value; label "From your project · LR-001" | "Sol draft · run …"; hidden solSuggestions[] += {field, source, runId?, suggestionId?, ref?, edited:false}
  → dialog Save → chapter command {type:'logical.responsibility', payload:{…, solSuggestions}}
  → worker: validates each 'sol' entry against a completed run of this owner/project containing that field (same check as adoptSavedIntelligence, intelligence-service.js:25); stamps acceptedBy = actor
  → domain apply: record.provenance.suggestions[] += entries; history += {event:'Accepted suggestions', fields}
  → operation_events kind 'suggestion' {formId, field, source, runId, outcome:'accepted'|'edited'}
Dismiss → POST /api/intelligence/feedback {runId?, formId, field, outcome:'dismissed', reason?}
```

Server-side, `mode:'field'` reuses `intelligencePacket` with a `parentObjectId` option (so a new record's packet is anchored on its parent — requirement, responsibility, capability, threat target — instead of throwing at `public/intelligence-context.js:32`), a `fieldDraft` contract shaped like `architectureDraftContract` (`{formId, commandType, recordId, fields:[{key,label,maxLength,current}], stamp}`), the existing budgets, disclosure policy (`aiPolicy.excludedObjectIds`, `enabled`), secret and contact redaction, the packet-stamp match on generate and the second-pass source check. The schema is `fieldDraft:[{field, value, rationale, sourceRefs}]` validated like `validateArchitectureDraft` (each field once, refs inside the packet, lengths, no numbers not in the packet — reuse `guardReasoning`'s number and over-claim checks, `public/brain-reasoning.js:500`).

### 4.4 UI: "suggested, not saved"

- A spark button in each module's `field()` helper: `<button type="button" class="spark" data-spark="<formId>:<field>" aria-label="Suggestions for <label>">`; class `live` only when a deterministic offer exists (never pulsing for nothing; no focus/typing trigger). Read-only roles get no spark.
- Popover anchored to the field, focus-trapped, Escape closes (same rules as the existing dialogs, audit UX-10/F-18): offers in the three bands with their label, ref/run id and `why`; buttons **Accept**, **Edit** (accept then focus the input), **Dismiss** (reason optional for a project offer, ≥ 8 chars for a Sol draft). "Draft with Sol" shows the packet first ("Sol will read N sources … Inspect what will be sent") and only then "Generate"; disabled with the one status line when no model is connected (I2-05).
- After Accept the input keeps a visible marker until saved: label suffix "From your project · LR-001" or "Sol draft · not saved", a dotted underline on the input, and a dialog footer line "2 fields carry suggestions — they are saved only when you save this record". Editing the input flips the marker to "edited". Nothing writes to the project until the dialog's Save, and the change review shows the provenance column.
- After save, the record shows the same marker in the companion's field list until the field is edited by hand; the SDD's record tables gain a provenance footnote (extend `reasoningRecordMarkdown`, `public/reasoning-record.js`).

### 4.5 Commands, provenance and doctrine checks

- Command payloads gain `solSuggestions[]`; the worker refuses `source:'sol'` entries whose run is not this owner/project's, not completed, or lacks the field; overwrites `acceptedBy`; keeps `Idempotency-Key` and revision checks unchanged (`worker.js:75`, `public/canonical-command.js`).
- Records store `provenance.suggestions[]` (not `origin:'suggestion'`, which stays reserved for whole-record ghosts).
- Doctrine: LLM output enters only via a saved run and a human command (C-19 kept); no owner, identifier, number, test result or approval is drafted (numeric fields excluded; `guardReasoning` number check; deterministic offers copy only recorded values with refs); candidate/discovery knowledge cannot produce offers (registry reads `knowledgeForContext` eligibility only); scoring and conformance untouched; tenant boundary as today (runs keyed by owner/project); secrets redacted by the existing packet path; `productionAccepted` unaffected.
- Tests: `field-spark-validate.mjs` (packet excludes numeric fields; schema rejects unknown fields and uncited values; foreign-run `solSuggestions` refused; provenance stored; dismiss writes an event) and a browser check that the spark opens, Accept fills the input, nothing is saved until Save, and the marker survives a redraw.

### 4.6 Effort and order

1. Provenance shape + spark shell + deterministic registry for Chapters 4, 8, 9, 10 (this section's table) — M.
2. Server `mode:'field'` + validator + popover "Draft with Sol" + feedback endpoint + telemetry — M.
3. Remaining chapters' deterministic sources and the guide's "confirm" band — S.
4. Aggregate acceptance statistics per field/source in the stewards' view (closes I2-17) — S.

- **Learning loop.** `stewardQueue` (`public/knowledge-stewardship.js:90`): dismissals and used/applied advice whose knowledge was withdrawn; `captureDraft:102` words a claim; Sol advises the stewards through `K:` items (`stewardshipReading:116`); a released, pinned, linked claim is read by `learnedFor:145` in every later packet for that record and takes precedence in the instructions.
