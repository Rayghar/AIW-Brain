Numbers, owners, products and identifiers are never drafted.

## 1. Summary (direct answers)

1. **Co-author in the archive is two layers.** A server "stage co-author" that drafts typed field operations (`append-objective`, `update-node-property`, …) with an OpenAI-backed gateway and a deterministic fallback, records them as a durable Brain transaction, and only applies them after approval, a 20-character rationale and a graph-freshness check (`A/apps/api/src/stageCoAuthorAssistant.ts`, `livingCanvasApplicationRoutes.ts:74-190,532-720`, `packages/engine/src/stageDraftApplication.ts`). On top sits a client "generative cursor" that lists chapter-derived proposals, previews the exact effect, requires the user to review values and give a reason, then saves through the chapter's own command (`A/apps/web-v5/src/studio/coauthor-session.ts`, `universal-generative-cursor.tsx`). The cursor layer calls no LLM.
2. **Ask Sol is one governed endpoint** (`POST /api/co-architect/ask`, `A/apps/api/src/projectIdentityApplicationRoutes.ts:1372-1470`) fed by a local deterministic kernel first, then an LLM answer that is schema-validated and grounded to allowed reference ids, with deterministic fallback (`A/apps/api/src/coArchitect.ts:1569-1830`). The client companion (`A/apps/web-v5/src/sol/companion.tsx`) has five jobs (Understand / Propose / Compare / Ask / Draft), context chips per selected object, and turns answers into actions only through explicit clicks: a per-field "Put this in <field>" draft, candidate dispositions with rationale, or "Answer on the desk".
3. **The spark ("field whisper") is deterministic and client-side.** `SolPulse` is a button in the field header that opens Sol scoped to that field (`A/apps/web-v5/src/studio/field-whisper.tsx:14-64`). Offers come from `suggestChapter` (text rules over what the person already typed, `lib/field-intelligence.ts:37-66`) plus a regex-ranked catalogue (`lib/sol-library.ts:107-129`) plus proposals distilled from the last Brain answer (`lib/sol-mind.ts:264-307`). Accepting writes the field in the browser draft with origin `sol-draft` and a ledger entry; the server sees it only when the chapter is saved through its normal preview-and-reconcile command.
4. **Autofill exists in the archive but is bounded:** `populateEmptyFields` fills *empty* Introduction fields from the person's own brief after intake or upload, labelled "Sol draft", without a per-field accept (`A/apps/web-v5/src/lib/field-intelligence.ts:68-93`; `prototype/introduction-stage.tsx:331,361,389`). Everything else needs a click.
5. **V5 already has the governed half:** server-recorded LLM runs with packet review, budgets and redaction (`V/intelligence-service.js`, `V/intelligence-provider.js`), a field-draft contract for architecture tasks (`V/public/architecture-drafting.js`), per-record "knobs" that Sol may refine through change review (`V/public/chapter-reasoning.js:53-80,316-331`), deterministic hints with a "Fill unanswered fields" button (`V/public/design-planner.js:46-49`, `design-task-ui.js:24,49`), and ghost proposals per chapter.
6. **What V5 lacks:** a spark on ordinary chapter form fields (Ch1-10 dialogs), an LLM field-draft mode for those forms, per-field provenance in the saved record, a unified suggestion list with accept/edit/dismiss and reasons, and acceptance telemetry.
7. **Adoptable as-is in concept:** field session shape (understood / why it holds / offers / next), honesty labels (from your project / drafted by Sol / confirm), the "reviewed before save" gate, reason-required reject/defer, source-fingerprint invalidation of stale suggestions.
8. **Must change for V5:** no React events — a shared `field-spark.js` hooked into each module's `field()` helper; LLM drafts must be server-recorded `intelligence_runs` (mode `field`) and enter the record only via the human's chapter command carrying `solSuggestions` provenance; no client-side canonical writes; bulk autofill only as an explicit reviewed action.
9. **Effort:** spark shell + deterministic sources M; LLM field-draft M; co-author panel M; Ask Sol upgrades S. Sequence: provenance + spark shell → deterministic sources Ch1-5 → LLM field draft → co-author panel → Ask Sol jobs → telemetry/tests.
10. **Doctrine:** every suggestion is proposed and individually accepted; numeric fields are never drafted; candidate/catalogue items carry labels and no scores; `productionAccepted` unaffected.

### 2.2 What is rule-based vs LLM

- Cursor proposals for Chapters 1-5 are computed in the browser from workspace state; the docs state the cursor "does not introduce another architecture authority or a separate AI provider" (`A/docs/j5-persistent-coauthor/IMPLEMENTATION.md:17`). "Prepare suggestions" only calls existing chapter generation (Decisions `onExplore`, `A/apps/web-v5/src/studio/decisions-coauthor.tsx:17`).
- The stage co-author route is the LLM path (hybrid by default, `livingCanvasApplicationRoutes.ts:79`), but its output is a candidate layer that cannot reach the graph without approval and the apply route.
- The `sageBrief` paragraph is deterministic (`A/apps/api/src/sagePlaybookBrief.ts:434-467`, `inventedEvidence:false, scoringUsed:false`).

### 2.3 Never-auto-answer rule

- Method questions are `neverAutoAnswer` (already noted in V5 audit C-06, `V/audit/04_CAPABILITY_DELTA.md:46`).
- Co-author: "Sol never accepts the chapter" (`coauthor-board.tsx:37`); rationale required (`coauthor-session.ts:68`); review-before-save (`universal-generative-cursor.tsx:194`); Introduction adapter refuses to draft `goals/purpose/users` from library examples (`introduction-coauthor.tsx:19`).
- Exception: `populateEmptyFields` after intake/upload/last interview beat writes derived text into empty Introduction fields without a per-field click (`prototype/introduction-stage.tsx:331,361,389`), labelled "Sol draft"/"just appeared" (`:820`). This is the one place the archive auto-fills.

### 2.4 Limits and unfinished parts (evidence)

- Candidate authority is "source-complete but authority-integration partial" (`A/docs/V5_GOVERNED_CANDIDATE_COAUTHORING.md:74`); the binding release "does not claim that the chapter command has been executed after a candidate selection" (`A/docs/V5_CANDIDATE_AUTHORITY_BINDING.md:49`).
- "Drivers / Decisions / Components Propose is still mostly display. No live accept from a ghost card." (`A/docs/V5_SOL_MENU.md:217`); `living-canvas/apply` is "Dark" (`A/docs/V5_INTRODUCTION_CLOSEOUT.md`, table row `living-canvas/apply`).
- Continuity: "database restart durability has not been exercised" (`A/docs/sol-continuity/IMPLEMENTATION.md`, section 1); persistent co-author: "Browser interaction, visual acceptance and target-database acceptance remain pending" (`A/docs/j5-persistent-coauthor/IMPLEMENTATION.md:9`).
- Feedback store is a single-process local file (`A/docs/j5-persistent-coauthor/IMPLEMENTATION.md`, "Saving and authority").
- `append-decision` writes `status:'accepted'` while the comment claims project-candidate state (`A/packages/engine/src/stageDraftApplication.ts:236-239`).

## 6. Adoption plan for V5

### 6.1 Spark (field-level intelligence)

**(i) Port as-is in concept.** The field session (understood / why it holds / current value / offers / next / teach); the honesty triage (From your project · Drafted by Sol · Confirm); the pulse only when there is something to offer; one tailor question at a time; suggestions never write without a click; stale offers invalidated when the source changes; the accept ledger.

**(ii) Must change.** No React or window events: one shared `V/public/field-spark.js` mounted by each module's dialog. Deterministic offers come from a per-form registry reading the project document (like `designHints`). LLM drafts must be server-recorded runs (`intelligence_runs`, mode `field`) with a packet the person sees first (`context` then `generate`), reusing budgets, disclosure policy (`aiPolicy.excludedObjectIds`, `enabled`) and redaction. Accept writes the input in the open dialog only; the value reaches the project through the chapter's normal command, which now carries provenance. Bulk autofill (`populateEmptyFields`) is not ported as an implicit step; it becomes an explicit "Fill empty fields from your project" action listing each field before it writes (same shape as `design-task-ui.js:49`). Numeric fields are never drafted.

**(iii) Concrete design.**

Data structures (client, `field-spark.js`):

```
FieldSpark session { formId, field, label, current, recordId|null, commandType,
  offers: [{ id, source:'project'|'sol'|'knowledge', value, why, refs:[...], runId?, suggestionId?, honesty }],
  understood, next }
```

Deterministic source registry (`V/public/field-suggestions.js`): `suggest(formId, field, p, formValues) -> offers[]`. Examples: `#l-responsibility-form.purpose` from the linked requirement description (`requirementIds`); `#q-driver-form.stimulus/response` from the linked requirement acceptance text; `#a-component-form.boundary` from allocated responsibilities; `#rt-editor.runbook` from `technologyRealisation.records[].operationsPlan`; `#i-editor.failurePolicy` from the realisation interaction `failure`. Every offer cites the record ref. No catalogue dump: at most 3 offers per field.

Server (extend `V/intelligence-service.js`, no new route family): `POST /api/intelligence/context` and `/generate` accept `mode:'field'` with a `fieldDraft` contract built like `architectureDraftContract`: `{formId, commandType, recordId|null, fields:[{key,label,maxLength,current}], stamp}` limited to the free-text fields listed in section 6.4; schema `fieldDraft:[{field,value,rationale,sourceRefs}]` validated by the same rules as `validateArchitectureDraft` (max 12, each field once, cited refs must be in the packet, lengths). The packet keeps the existing `S1` selected-object rule for saved records; for new records the packet's selected object is the parent record chosen in the form (requirement, responsibility, capability, threat target), so `intelligencePacket` needs a `parentObjectId` option instead of throwing at `V/public/intelligence-context.js:32`. Runs are stored as today (`intelligence_runs` + FILES) and replayable by id.

Provenance/command shape: every chapter save command may carry
```
payload.solSuggestions: [{ field, source:'project'|'sol', runId?, suggestionId?, ref?, acceptedBy, acceptedAt, edited:boolean }]
```
The worker validates on `/api/commands`: `source:'sol'` entries must name a completed `intelligence_runs` row of this owner/project whose result contains that `field` (same check as `adoptSavedIntelligence`, `V/intelligence-service.js:25-28`); `acceptedBy` is overwritten with the authenticated actor. Domain save functions store it on the record as `record.provenance.suggestions[]` and push a history event `{at, event:'Accepted Sol suggestions', fields:[...]}` (mirrors `assistedDrafts` at `intelligence-context.js:156-157`). `origin:'suggestion'` on the record stays reserved for whole-record ghosts.

UI: a spark button beside the label in each module's `field()` helper (`<button type="button" class="spark" data-spark="<formId>:<name>" aria-label="Suggestions for <label>">`), `live` class when a deterministic offer exists. Click opens a small popover anchored to the field: "From your project" offers first (with ref), a "Draft with Sol" button (shows the packet sources, then generates), and for each offer Accept / Edit / Dismiss. Accept sets the input value, marks the label "Sol draft" or "From your project", appends to a hidden `solSuggestions` JSON input; Edit = Accept then focus; Dismiss records a local dismissal and posts feedback. Keyboard: the button is in tab order; the popover traps focus and closes on Escape (same rules as the existing dialogs, audit UX-10/F-18). Read-only roles get no spark (`V/worker.js:68` role gate covers writes).

Telemetry: `operation_events` kind `suggestion` written (a) by the worker when a command carries `solSuggestions` (`{formId, field, source, runId, outcome:'accepted'|'edited', actor}`) and (b) by a new `POST /api/intelligence/feedback {runId?, formId, field, outcome:'dismissed', reason?}` (Origin-checked like `/generate`). Reason optional for dismiss of a deterministic offer, required (≥ 8 chars) for an LLM draft, mirroring `v5CoauthorFeedbackRoutes.ts:30`.

Tests (Node validators in the existing style): `field-spark-validate.mjs` (packet excludes numeric fields; schema rejects unknown fields and uncited values; a command with `solSuggestions` naming a run of another project is refused; accepted provenance is stored; dismiss writes an event), plus a browser check in `*-browser-validate.mjs` that the spark opens, an accept fills the input, and nothing is saved until the dialog's Save.

**(iv) Effort/sequence.** Shell + provenance + deterministic sources for Ch1-5: M. LLM field draft (server mode, validator, UI): M. Ch6-10 deterministic sources: S. Order: 1 → 2 → 3.

**(v) Risks vs AGENTS.md.** Auto-answer: prevented by design (popover accept per field; no bulk fill without a reviewed list). Invented measures: numeric fields excluded from the LLM contract; deterministic offers only copy recorded numbers with their ref. Candidate knowledge affecting scoring: offers carry labels and no scores; knowledge offers cite the receipt and require the catalogue's eligibility (`knowledgeForContext`). Silent mutation: the value only enters through the person's command with revision check and idempotency key. Tenant/project boundary: runs and feedback keyed by owner/project as today. Secrets: existing packet redaction applies to the field-draft packet.

### 6.2 Co-author

**(i) Port as-is.** The proposal contract (`title, why, effect, sourceRefs, fields[{key,label,value,before}], ghosts, costs, obligations`); the fingerprint that invalidates a proposal when the source changes; review-before-save; reason-required reject/defer; a history that supports "reconsider"; the saved-source reading (`empty/working/accepted/stale`) with prerequisite chapter.

**(ii) Must change.** V5 has no per-chapter workspace repositories; readings are computed from the project document (`chapterSummaries`, findings, `chapterGuide`). Accept opens the chapter's existing "Review & edit" dialog prefilled (`editArtefact(id, proposal)`, `editDriver(null, proposal)`, `editGhost()`), so the save path and its checks are unchanged. The stage co-author LLM operations (`append-objective` etc.) map to V5's `intelligence.generate mode:'design'` → `design.start`; no canonical-commit ledger is ported (V5 baselines and four-eyes review, audit C-02, remain the acceptance path).

**(iii) Concrete design.** `V/public/coauthor-ui.js` rendered in the Sol panel's design view (`brain-context-ui.js:41-45` `designView`) and in each chapter's assistance nav: a "Suggestions · N" section listing proposals `{id, fingerprint, chapter, title, why, effect, sourceRefs, open()}`; dispositions stored in the project document under `coauthoring.suggestionFeedback[]` via a new command `coauthor.disposition {fingerprint, title, outcome, reason, sourceRefs}` (reason ≥ 8 for rejected/deferred), so they travel with the project and the change journal; accepted outcomes are recorded automatically when the opened dialog saves with `payload.proposalFingerprint`. A "Resume" note per chapter/tab per actor can reuse `companion-drafts.js` (already captures guide inputs) plus a `coauthor.checkpoint` command; keep it single-document, no new tables.

**(iv) Effort.** M (panel, dispositions command, dialog prefill hooks in ~6 editors, tests). After the spark.

**(v) Risks.** No new authority: the panel never saves; dialogs do. Do not port `append-decision` with `status:'accepted'` semantics. Keep candidate/discovery knowledge out of proposal ranking (use only project records and approved receipts).

### 6.3 Ask Sol

**(i) Port as-is.** Five jobs with preset prompts per chapter/object; prompt retained per context and flagged stale on source change; "Answer on the desk" hand-off; "Put this in <field>" for drafts; a receipt strip (execution mode, knowledge release, run id, "Proposal only").

**(ii) Must change.** V5 already keeps a packet-first flow (`prepare` → `generate`) and two-pass source checking; keep it. Map jobs to existing modes: Explain → `author`/`reason`, Suggest → `design` options, Compare → `reason` on decisions (`D:` targets), Check → `challenge`, Draft → new `field` mode (6.1). Replace the in-memory `states` map in `intelligence-ui.js:7-9` with the per-context retention `companion-drafts.js` already provides.

**(iii) Concrete design.** In `intelligence-ui.js`: job buttons above the composer that set a preset prompt (never send); a "Draft for a field" job that opens the spark popover for the currently open dialog field; a run history list per object already exists (`refresh`, `runs?object=`); add the receipt strip fields (`run.provider/model/id`, `groundingReview.accepted`, packet stamp). Keep `intelligence.adopt` as the only way a run's text enters the project for passages/design/challenges; field values go through 6.1.

**(iv) Effort.** S. After 6.1.

**(v) Risks.** Preset prompts must not embed product suggestions; keep "Send is explicit". Do not add a `decide` job (retired on purpose in the archive, `A/docs/V5_SOL_MENU.md`).
