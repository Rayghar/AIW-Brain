# Run AIW V5 locally

Current source package: `AIW-rc41-source.zip`, release `AIW v0.10.0-rc.10.73.41+studio.20261022`. It contains the frontend, backend, shared model, schema migrations, package lock, checks and release evidence. It does **not** contain your hosted projects, local database, dependencies, repository originals, workbook, or secrets. A Site deployment and its commit are recorded separately; possession of this ZIP does not establish that a hosted trigger or AI provider is configured.

## Start

1. Install **Node.js 24**. Confirm with `node --version` (it should start with `v24.`) and `npm --version`. The server refuses to start on Node.js older than 22.13, where its built-in SQLite database is unavailable; Node.js 22 works but prints an "experimental" warning.
2. Unzip `AIW-rc41-source.zip`. Open a terminal **inside** the extracted `AIW-rc41-source` directory, where `package.json` and `server.js` are located.
3. Run:

   ```sh
   npm ci
   npm start
   ```

4. Open **http://localhost:4173** in your browser. Keep the terminal open. Stop the server with **Ctrl+C**.

The first visit loads an illustrative Bank Payment Journey. Choose **All projects** to create a blank project or another reference copy. Your changes persist in two places that belong together: the SQLite database `.aiw-local/project.sqlite` (project rows, access, activity, receipts) and the object directory `.aiw-local/baselines/` beside it (frozen baselines, the change journal, uploaded workbooks, attachments, Sol's saved responses). Both are created automatically on first run. **A backup is the database file and the object directory together**; a copy of `project.sqlite` alone opens, but every project that references an object answers with an integrity error (HTTP 422, `code: integrity`) rather than loading. `AIW_LOCAL_DB` moves the database and, with it, the object directory (always `baselines` next to the database file unless `AIW_LOCAL_FILES` names another directory). The local backend uses a development identity for one architect and is meant for local development, not production authentication.

If port 4173 is busy, run `npm start -- --port 5173` and open **http://localhost:5173**. For automatic server restarts while editing files, use `npm run dev`. Ctrl+C (or a supervisor's SIGTERM) stops the server in order: it stops accepting connections, lets requests in flight finish (five seconds at most), closes the database and exits 0. `GET /api/health` answers without sign-in with the release, the database and object-directory checks and whether Sol is configured; a supervisor can poll it. Every answer carries an `X-Request-Id`, and every server error is one JSON line in the log with that id.

The server bounds what it reads: a request body is read only after the address, route and session checks, within the route's limit (1.5 MB for commands, 12 MB for uploads, recovery and attachments, 1 MB otherwise), and a larger body is refused with HTTP 413 before it is buffered. Headers must arrive within 30 seconds and a complete request within two minutes (`AIW_REQUEST_TIMEOUT_MS`). API answers travel gzip-compressed when the browser accepts it.

Retention runs at start-up and then hourly (`AIW_RETENTION_INTERVAL_MS`), and on demand with `node scripts/retention.mjs` (`--dry-run` only reports). The policy, in days and adjustable per class with `AIW_RETENTION_*`: Sol's runs and retrieval packets with their files after 90 days; operation events and the activity feed after 365 days; uploaded workbooks that were never applied to a dataset after 30 days; idempotency receipts after a day; a Sol run still pending after ten minutes (the server stopped mid-request) is marked interrupted and its token reservation is released. Projects, baselines, the change journal, applied workbooks and their source snapshots, and attachments are never swept: they are the project's evidence for as long as the project exists. A save deletes the objects it superseded (an earlier change-journal segment or knowledge file) once they are ten minutes old, and Sol's semantic index is one object per project.

The server accepts connections from this computer only (`127.0.0.1`). It also answers only to its own address: a request whose `Host` is an IP address or `localhost` is served, and any other name is refused (HTTP 421). This stops a web page you visit from reaching the workbench through a DNS trick. If you open it under a host name, list that name in `AIW_ALLOWED_HOSTS` (comma-separated, for example `AIW_ALLOWED_HOSTS=workbench.lan`).

To try AIW from a phone or another device on the same network, add local accounts (below) and start it with `npm start -- --host 0.0.0.0` (or set `AIW_HOST`); stop it when you finish. Without local accounts the backend has no sign-in, so anyone who could reach it would open and change your projects as the development architect and use a configured OpenAI key. The server therefore refuses to listen beyond this computer without accounts. Only on a network you fully trust, `AIW_ALLOW_OPEN_NETWORK=1` overrides that refusal.

When the workbench is only served over HTTPS, set `AIW_COOKIE_SECURE=1` so the session cookie is marked `Secure`. Behind a TLS-terminating proxy that sets `X-Forwarded-Proto: https`, set `AIW_TRUST_PROXY=1` as well: only then is that header honoured, so a client cannot spoof it. A sign-in form post must come from the workbench's own page (its `Origin`, or `Sec-Fetch-Site: same-origin` from a browser that omits `Origin`).

Every setting the workbench reads is listed in `.env.example`, which is rendered from the table in `settings.js` (`node scripts/env-example.mjs`); the server-hardening suite fails when the two drift. With local accounts, a project or organisation role can only be granted to an account in `AIW_LOCAL_ACCOUNTS`.

Every page is served with a Content-Security-Policy that allows only the workbench's own scripts, and static files are compressed (brotli or gzip) and revalidated by ETag. `npm run test:server-hardening` checks these defences.

## Production build

`npm start` serves the source modules in `public/` as they are, which suits editing. For everyday use, `npm run start:production` first builds the client (`client-bundle.mjs`, with esbuild) and then serves it: the modules become a few minified, content-hashed chunks that load in parallel, and the 40 stylesheets become one minified file. The hashed files are cached by the browser for a year and never go stale, because a change produces a new name. On the reference project a Chapter 4 Model page then makes about 70 requests instead of about 210. `npm run build` produces the same client in `dist/client` next to the packaged Worker, and `npm run test:bundle-browser` checks every chapter and tab of the bundle under the Content-Security-Policy. To serve an existing build, run `node server.js --client dist/client`.

`npm run build` also packages the hosted Worker in `dist/server`: the API modules it copies by following the import graph from `worker.js`, an entry `index.js` with a `fetch` handler and a `scheduled` handler that consumes one queued or expired drafting-job slice and applies the retention policy, and the client assets embedded gzip-compressed (a browser that accepts gzip receives the stored bytes; any other client receives them decompressed; each encoding has its own ETag). The build imports the package and fetches every embedded asset back before it succeeds. `dist/.openai/hosting.json` names the bindings (`DB` for the database, `FILES` for objects) and `dist/.openai/drizzle` holds the migrations. **The hosted platform must register a recurring scheduled trigger** (a minute is suitable) for unattended drafts; this repository does not verify that the platform applies migrations or installs that trigger. The local Node server consumes one durable slice on startup and every ten seconds by default (`AIW_DRAFTING_INTERVAL_MS` sets 0 for startup only, or a positive interval in milliseconds). An active lease prevents a second runner from taking the job; an expired lease is resumed from its checkpoint. No provider is called without a configured key and the project owner's AI policy. A draft still requires a person to review every page before applying it.

## Two people on one machine (local accounts)

A knowledge claim is used only after someone other than its author has verified it (four eyes). By default the local server serves everyone as one architect, so a claim cannot complete its review locally. To let two people work on one machine, add named accounts to `.env`:

```sh
AIW_LOCAL_ACCOUNTS={"architect":"a-long-private-secret","reviewer":"another-long-private-secret"}
```

Each secret must be at least 16 characters, and each person keeps their own. Start with `node --env-file=.env server.js`. Each person then signs in at `/local/sign-in` and signs out at `/local/sign-out`. Sessions last 12 hours; signing out ends the session on the server at once, and all sessions end when the server restarts. After five wrong secrets for an account (or from one address), sign-in is locked for a period that doubles with each further failure, up to 15 minutes. Sign-ins, failures, locks and sign-outs are written to the server log as JSON lines. The owner of a project adds the other person as an **editor** in Project team, and that person then reviews claims in Mind Factory. The same rule holds for the design deliverable: approval evidence for a frozen Chapter 11 baseline is recorded by a second signed-in person, not by the architect who recorded its review, and only such an approval unlocks the delivery handoff. Two accounts are two people only when two different people hold them. `npm run test:local-accounts` checks sign-in and four eyes through the server.

## Where the code lives

| Part | Files | Purpose |
| --- | --- | --- |
| Frontend | `public/index.html`, `public/entry.js`, `public/app.js`, `public/*.js`, `public/*.css` | Chapter UI, connected canvas, Sol and Mind Factory, browser-based model interactions. |
| Local backend | `server.js`, `local-db.js`, `local-files.js`, `settings.js`, `retention.js` | Node HTTP server; SQLite (WAL) and file adapters for local use; the settings table; the retention policy and sweep. |
| API and services | `worker.js`, root `*-service.js`, `project-storage.js`, `brain-retrieval.js`, `intelligence-provider.js` | Project commands, storage, review, export and optional AI gateway. |
| Shared model | `public/*-domain.js`, `public/architecture-model.js`, `public/perspective-view.js` | Domain rules and canonical model used by the frontend and API; the perspective view draws any concern of it in every chapter's Model switcher. Keep the original paths intact. |
| Schema | `drizzle/*.sql`, `db/` | Database migrations and schema. Local SQLite migrations apply automatically, each in one transaction, and the server records each file's SHA-256: a migration file edited after it was applied stops start-up. Change the schema in `db/schema.ts` and run `npm run db:generate` for a new migration. |

The hosted deployment uses the same app logic with managed D1/R2 bindings; `server.js` supplies local substitutes. You do not need to run a separate frontend server or configure a database for local use.

## Check it

Run `npm run check`, `npm run test:connected-model`, and `npm run test:investigation`. The investigation check covers Chapter 4–11 object continuity, scoped relationships and the reviewable contract-to-SDD change. Tests do not prove a real Orbus import, independent knowledge quality or provider behaviour.

The full gate is `node release-checks.mjs`: it runs every `test` and `test:*` script, three at a time, and writes a JSON report (set `AIW_REPORT` to choose where). The DOM suites use `happy-dom` and the browser suites use Playwright; both are pinned development dependencies, so `npm ci` installs them. Run `npx playwright install chromium` once for the browser suites (or point `AIW_BROWSER_EXECUTABLE` at an installed Chromium). `npm run test:intake` imports a synthetic 1,400-row workbook of the shape of a real assessment workbook (generated by `scripts/synthetic-workbook.mjs`, no client text) and runs the intake acceptance workload on it; with `AIW_WORKBOOK` set it runs on that file instead. Two checks need files that are not in the repository and run only on request: `npm run verify:enhancements-ui` needs a workbook in `AIW_WORKBOOK`, and `npm run verify:repository-packet` needs a repository packet in `AIW_PACKET_PATH`.

`npm run release:manifest -- --out manifest.json` lists every tracked file with its SHA-256; `npm run release:verify -- manifest.json` checks a copy against it. The manifest is integrity evidence only; it approves nothing. The same gate runs in GitHub Actions (`.github/workflows/v5-release-checks.yml`) and keeps its report and manifest as build artifacts.

## Optional AI connection

The model and rule-based guidance work without an API key. To connect Sol locally, copy `.env.example` to `.env`, put your own key in `ANTHROPIC_API_KEY` (Sol then asks for `claude-opus-5-5` at `AIW_LLM_EFFORT=medium` unless you set others), or in `OPENAI_API_KEY` for OpenAI (Sol then asks for `gpt-4.1-mini`; `AIW_LLM_MODEL` names another model, and `AIW_LLM_PROVIDER` chooses when both keys are set), and start with `node --env-file=.env server.js`. A key alone connects. Do not put a key into browser code, commit it, or share the `.env` file. AIW shows **LLM not connected** until configured, naming the selected provider and the variable still to set; `GET /api/intelligence/status` names the provider, the model and the effort, never the key. Requests sent to Anthropic are kept under your account's API data-retention terms; OpenAI requests are sent with `store:false`. Once connected, Sol also reasons at the review desk (Chapter 11 → Model, or Validate → Review desk) and in the companion of every chapter model, Chapters 2 to 10 (select a record, or ask for the chapter's round), and for the knowledge stewards (Mind Factory → Architecture in context → Stewards). *Ask Sol* shows what will be sent before anything leaves your machine. To route requests through a gateway, set `AIW_ANTHROPIC_BASE_URL` (Anthropic Messages API) or `AIW_LLM_BASE_URL` (OpenAI-compatible); https, or http on loopback. Each key is sent only to its own provider's address. The project owner's policy (Operations) allows 0–120 of Sol's requests an hour per project, 30 by default, within the daily token budget.

To carry a hosted project into your local workspace, export its connected project JSON from the hosted project's Chapter 11 Output, then use **All projects → Restore / import project** locally. Review the import preview before applying it; hosted project data is intentionally absent from this source download. The complete recovery package (document, originals, attachments, reviews, discussions, activity) can be exported by the project owner and editors only. A restored project keeps its review history as historical assertions: the people who recorded the architect review, froze baselines or recorded approval on the other workbench are kept as `importedActor`, not as signed-in identities here, so approval evidence and the delivery handoff need an architect review recorded on this workbench and a second signed-in person.

**Checking the live connection.** `npm run sol:live-check` starts a server on a scratch database with the shell's key (`OPENAI_API_KEY` or `ANTHROPIC_API_KEY`; `AIW_LLM_MODEL` only to name another model), creates a project from a reference brief and a reference project, asks Sol for one field draft in each of the eleven chapters of the reference project and once in the journey and review modes, waits for each run and writes `evidence/sol-live/<date>-<provider>.json`: the provider, the model, the prompt pins, each run's status, stop reasons and usage, what the checks accepted or withheld, and for each chapter's field draft the size of its packet, its grounding and the draft text, so the drafts' relevance can be judged. No prompt content and no key are written; nothing Sol returns is applied. It exits 0 when every run completed, 1 when one failed and 2 when no key is set (nothing was sent). Each run also records (schema `aiw.sol-live-check/4`) its packet stamp and an outcome: what was offered and withheld, which layer withheld it (the deterministic guard, the model's source check, or both), and the fallback that stands; the totals add them up per mode, and a withheld draft is kept with `offeredToArchitect: false`. `completed` says every run completed; `passed` is its deprecated alias and is not acceptance. `--mock` runs the same probe against the test double to prove the probe itself, `--mock-faults` adds the double's deliberate faults (an invented number, a guarantee, a gap statement, a rejecting and a self-contradicting check), and `npm run test:sol-live-check` does both in the release gate (eleven chapter entries, each with its draft; each fault withheld by its layer); the live run with a key is not part of `node release-checks.mjs`, which runs without keys.

## Optional knowledge repository (on the laptop that holds the corpus)

The acquired architecture corpus becomes searchable in Mind Factory → Sources when the knowledge repository service runs beside the workbench. From this directory:

```sh
npm run repository:init     # once: a service token and a notice key under %LOCALAPPDATA%\AIW\repository-service
npm run repository:build    # index or re-verify the corpus (about a minute)
npm run repository:serve    # keep it running; it listens on http://127.0.0.1:4180 only
```

`repository:init` prints three settings. Add them to `.env` (never commit it) and start the workbench with `node --env-file=.env server.js`. Without them, Sources shows the bundled locators as before. Search results are unreviewed repository text: retrieving one saves the exact original into the project, and it becomes knowledge only through interpretation, review, release and activation. See [KNOWLEDGE-REPOSITORY.md](KNOWLEDGE-REPOSITORY.md), including the live refresh from GitHub and the optional daily task.

For a hosted private project, the laptop's loopback repository service is unreachable from the hosted Worker. Use `repository-service/cli.mjs transfer` to sign one to five exact current originals for that project's tenant and project IDs, with a stated use purpose and source-rights acknowledgement. Configure the corresponding public notice key in the hosted `AIW_REPOSITORY_NOTICE_KEYS` setting; the private signing key stays on the laptop. In that project's **Mind Factory → Sources**, upload the private transfer file, inspect its file paths and purpose, and acknowledge the exact revisions before importing. The file carries original text, so keep it out of the source ZIP and repository. Imported sources remain unreviewed; an independent claim review and separate release receipt are required before architecture guidance can use them. The precise command, scope, and trust-key setup are in [KNOWLEDGE-REPOSITORY.md](KNOWLEDGE-REPOSITORY.md).
