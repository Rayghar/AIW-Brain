# AIW rc.10.71.1 Architecture and Intelligence Authority Design

Generated: 2026-07-13T12:00:45Z

## Design objective

rc.10.71.1 converts AIW from several intelligent features sharing common libraries into one governed project-design intelligence system. The controlling principle is:

> **One Brain, one canonical model, one governed knowledge manifest, one proposal receipt and many interaction surfaces.**

The change is structural. Existing specialist implementations were retained only where they provide bounded task logic; they no longer own LLM routing, canonical context loading or mutation authority.

## Target runtime

```text
User gesture or stage task
        ↓
Canonical project load + branch/revision check
        ↓
AIW Brain Orchestrator
        ├── deterministic Kernel and engine rules
        ├── approved Architecture Knowledge manifest
        │     ├── Pattern DNA
        │     ├── Cambridge rules
        │     ├── approved repository-derived knowledge
        │     └── enterprise rule packs
        └── optional governed LLM enrichment
        ↓
Candidate fusion, validation and proposal receipt
        ↓
Preview / explain / challenge
        ↓
Architect accepts, edits or rejects
        ↓
Canonical model mutation, audit and semantic impact
```

## Authority boundaries

| Layer | Responsibility | May directly mutate canonical architecture? |
|---|---|---:|
| Canonical Architecture Model | Accepted project truth, revision, lineage and stage state | No |
| AIW Brain Orchestrator | Loads context, invokes bounded capabilities, assembles one response and receipt | No |
| Deterministic Kernel/engine | Eligibility, validation, ranking limits, transformation and safety rules | No |
| Approved knowledge | Patterns, tactics, methods, evidence, policies and obligations | No |
| Governed LLM | Ambiguity interpretation, structured drafting, alternatives and explanation | No |
| Brain Signal projection | Converts governed results into hints, warnings and blockers | No |
| Architect | Accepts, edits, rejects and authorises canonical change | **Yes, through governed commands** |
| Mind Factory | Ingests, reviews, promotes and releases knowledge | Knowledge governance only |

## Orchestrated architecture tasks

The Brain Orchestrator now owns eleven project-design task methods:

1. Workspace intelligence projection
2. Design-brief analysis
3. Requirements distillation
4. System Context candidate compilation
5. Stage Co-Author drafting
6. Living Canvas action generation
7. Ranking explanation
8. Stage advice
9. Ask Sol explain/challenge
10. Architecture synthesis
11. Assisted architecture audit

Routes provide project identifiers and expected revisions rather than posting an arbitrary project object. The server loads canonical repository state and rejects stale context.

## One proposal receipt

Every project-design response can carry the same `ArchitectureBrainProposalReceipt`, including:

- project, branch and canonical revision;
- task, stage and scope;
- context fingerprint;
- application, Kernel and lifecycle grammar versions;
- knowledge release, Pattern DNA and Cambridge ruleset IDs;
- enterprise policy packs and LLM authority policy;
- authority contribution chain;
- deterministic rules and knowledge references;
- governed LLM route/model/request trace where used;
- human-approval and stale-revision controls;
- warnings.

The manifest is fingerprinted. Enterprise KMS signing remains an external acceptance item and is not represented as complete.

## Knowledge coherence

The concepts are assigned non-overlapping responsibilities:

- **Sol** is the user-facing co-author.
- **Architecture Brain** is the orchestrated project-design intelligence behind Sol.
- **Kernel** is the deterministic authority inside the Brain.
- **Pattern DNA, Cambridge, approved GitHub-derived claims and enterprise policies** are governed knowledge assets referenced through the manifest.
- **Mind Factory** is the knowledge supply chain, not a second project-design brain.
- **Living Canvas, Stage Co-Author, Ask Sol, synthesis and review** are interaction surfaces over the same Brain.

Operational health probes and Mind Factory extraction/promotions may use the provider gateway directly because they are explicitly classified control-plane or knowledge-supply-chain paths. They cannot mutate project architecture.

## Typed Architecture Context Graph

The graph contains 15 node kinds and 16 edge kinds. It connects:

- source → evidence → requirement;
- stakeholder → concern/requirement;
- requirement → quality driver and journey;
- journey → participant → interaction → participant;
- quality driver → constrained interaction;
- journey → architecture obligation;
- requirement/journey → context package;
- requirement/journey/evidence → architecture object;
- provider/evidence → interface → consumer;
- linked records → decisions and findings.

Stage slices expose unresolved and stale records by lifecycle stage. Requirement semantic changes traverse outgoing lineage and mark only durable downstream architecture objects, interfaces, decisions and findings stale. Newly compiled sources, requirements, journeys and context packages remain current.

## Requirements reconciliation

Conflict detection covers potential duplicates, negation-based contradictions and conflicting numeric targets. The system never selects a winner silently:

1. conflict appears with linked records, severity and rationale;
2. architect selects `resolved`, `accepted-variance` or `false-positive`;
3. a meaningful resolution rationale is mandatory;
4. open selected conflicts block canonical acceptance;
5. accepted conflict disposition is revision-checked, audited and reflected in requirements health.

The detection algorithm is intentionally advisory. It is not a substitute for semantic/legal interpretation.

## Legacy migration

A one-time migration projects existing objectives, constraints, assumptions, stakeholders and in-scope capabilities into the canonical Requirements Intelligence model. The receipt explicitly records `canonicalAuthority: requirements-intelligence`. Legacy fields remain compatibility projections while downstream consumers are migrated; they are not a second authority.
